Set `METRICS_ADDR` (for example `:9090`) to serve Prometheus metrics at `/metrics` on a listener of its own. It has **no authentication**: allow only your monitoring system to reach it (the Kubernetes example overlay has a NetworkPolicy from the `monitoring` namespace and an example `ServiceMonitor`).

Labels never carry user, key, service account, team or request IDs. Gateway, server and provider slugs are limited to existing objects (at most `METRICS_MAX_OBJECTS`, 200 by default, each; then `other`), and their series are dropped when the object is deleted.

| Metric | Labels |
|---|---|
| `omp_build_info` | `version`, `commit` |
| `omp_mcp_requests_total`, `omp_mcp_request_duration_seconds` | `method` (MCP methods, `notification`, else `other`), `outcome` |
| `omp_mcp_call_duration_seconds` | `gateway`, `server` (buckets from 5 ms to 120 s, as in usage) |
| `omp_mcp_rate_limited_total` | `limit` (`person_per_minute`, `credential_per_minute`, `service_account_per_minute`, `gateway_per_minute`) |
| `omp_payload_captures_total`, `omp_payload_capture_errors_total`, `omp_payload_redactions_total` | `rule` (redactions) |
| `omp_provider_token_refresh_total` | `provider`, `result` (`ok`, `refused`, `unavailable`) |
| `omp_server_health_checks_total`, `omp_mcp_servers` | `result` / `state` (`healthy`, `failing`, `unknown`) |
| `omp_http_requests_total`, `omp_http_request_duration_seconds` | `route` (the registered pattern), `method`, `code` (`2xx`, …) |
| `omp_retention_deleted_total`, `omp_retention_last_success_timestamp_seconds` | `kind` |
| `omp_usage_rollup_last_success_timestamp_seconds`, `omp_loop_leader` | `loop` |
| `omp_notifications_emitted_total` | `event` |
| `omp_notification_deliveries_total` | `channel`, `event`, `outcome` |
| `omp_notification_emit_errors_total` | |
| `omp_automation_token_auth_total` | `result` |
| `omp_agent_token_total` | `result`: `ok`, `ignored_not_relay` or `rejected_<reason>` (see [Agent identity tokens](#agent-identity-tokens)) |
| `omp_db_pool_*` | Connections acquired, idle, total and maximum; acquires, empty acquires and wait time |

Plus the Go runtime and process collectors. `omp_mcp_requests_total` counts requests to `/mcp/{slug}` that reached a gateway.

## Agent identity tokens

`omp_agent_token_total{result}` counts the agent identity tokens the portal looked at (see [Agent platforms](/docs/administer/agent-platforms)). `ignored_not_relay` is a token sent with a credential that isn't a relay account's key: the call went on as that credential's own. `rejected_<reason>` is a token on a relay account's request that failed a check, so the request was refused: the reasons are `malformed`, `algorithm`, `key_id`, `type`, `untrusted_issuer`, `disabled_issuer`, `unknown_kid`, `jwks_unavailable`, `signature`, `audience`, `principal_type`, `claims`, `person_issuer`, `expired`, `not_yet_valid`, `lifetime`, `replay`, `other_platform` and `tool_mismatch`. A refused token leaves no call record, so this counter and a warning in the log are where such attempts show.

## Dashboards and alert rules

Since v0.3.1 the repository ships **five Grafana dashboards** (MCP traffic, MCP servers, providers and tokens, notifications, platform) and **14 Prometheus alert rules** with unit tests and a runbook entry each, built from the metrics above. A test checks every metric and label they use against the portal's metric registry. v0.3.1 adds no metric. [Tracing, dashboards and alerts](/docs/operate/tracing#dashboards) has the list, how to load them and `make prom-check`; the example overlay has a `PrometheusRule` beside the `ServiceMonitor`. They have not been checked against live data.

## Useful alerts

Conditions worth alerting on, whether or not a shipped rule covers them:

- `omp_payload_capture_errors_total` increasing: recordings are failing (calls still succeed).
- No replica with `omp_loop_leader{loop="retention"} == 1` for an hour, or `omp_retention_last_success_timestamp_seconds` too old: old data isn't being deleted.
- `omp_usage_rollup_last_success_timestamp_seconds` older than 15 minutes: dashboards are stale.
- `omp_mcp_servers{state="failing"} > 0`: a team's server is down.
- `omp_notification_emit_errors_total` increasing: a change couldn't record its notification (the change itself succeeded). No replica with `omp_loop_leader{loop="notifications"} == 1`: nothing is being delivered.
- `omp_agent_token_total{result=~"rejected_.*"}` increasing: a platform's agents are being refused (a wrong issuer or audience, keys that can't be fetched, a tool name that doesn't match). `jwks_unavailable` means person calls from that platform fail.
- A high rate of `omp_mcp_rate_limited_total`, or of `omp_provider_token_refresh_total{result="unavailable"}`.

Traces are covered in [Tracing, dashboards and alerts](/docs/operate/tracing). They link to metrics only through the trace id on a call's record: exemplars are not built.
