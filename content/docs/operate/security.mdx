description: "What Open MCP Portal protects and how: authentication, per-request authorization, the identity token, credentials at rest, the address guard, consent links, records and reporting vulnerabilities."
---

Open MCP Portal stands between AI clients and your teams' MCP servers. Its job is that every call is made by someone allowed to make it, that servers know who is calling, and that no credential ends up where it shouldn't.

## Callers

- **People** sign in to the web app through your OpenID Connect provider (authorization code with PKCE and a nonce). Browser sessions are server-side; the cookie holds a random secret whose SHA-256 digest is stored. Writes need a CSRF token and a same-origin `Origin`. Sessions can also end after inactivity (`SESSION_IDLE_TIMEOUT`, off by default), and people list and end their own under Account › **Sessions**; platform admins can end all of a person's. A suspended person's sessions never come back: after reactivation they sign in again.
- **MCP clients** sign in with the portal's own OAuth 2.1 authorization server: PKCE S256 only, exact redirect URI matching, a token bound to one gateway (`resource`), consent per person, client and gateway, refresh tokens rotated on every use with reuse detection and, since v0.2.2, an absolute lifetime (`OAUTH_REFRESH_ABSOLUTE_TTL`, 180 days from the person's last sign-in of the app). Client ID Metadata Documents are fetched through the address guard (at most 16 KiB, no redirects), and only after the person has signed in. A trusted client asks once, with a short notice, the first time it signs in from a person's computer. Self-registered clients are marked unverified and can never be trusted to skip consent; the portal keeps at most `OAUTH_MAX_REGISTERED_CLIENTS` of them at once (1,000 by default), at most `OAUTH_MAX_UNUSED_CLIENTS_PER_ADDRESS` unused ones per address, deletes unused ones after 24 hours, and an admin can turn open registration off (see [Hardening status](#hardening-status)).
- **Keys** (personal and service account) always expire (at most 365 days) and can be limited to some gateways and to a [tool scope](#tool-scopes-and-curation).
- **Automation tokens** (`ompadm_`, `omppub_`) let CI call part of the management API, for example through the [`omp` command line](/docs/api/cli). They are separate from MCP credentials in both directions: they never work on `/mcp`, and `omp_`, `omp_sa_` and OAuth tokens never work on `/v1`. They expire (at most 365 days), show once, and are created and revoked only in a browser session, never with a token. A platform token stops working if its creator is no longer a platform admin. What they may do is fixed by the OpenAPI description, and they can't approve, delete, change roles or read recorded call contents. Every action is audited as the token. See [Automation tokens](/docs/administer/automation-tokens).
- **Provisioning tokens** (`ompscim_`) let one identity provider manage people and groups at `/scim/v2` only: they never work on `/v1` or `/mcp`, and sessions and other tokens never work on `/scim/v2`. See [Provisioning](#provisioning-scim).
- **No external identity.** A request to `/mcp/{slug}` that carries an `MCP-Gateway-Identity` header is refused with `403` before authentication, in both protocol eras. Agent platforms and relay accounts were retired in v0.4.0 ([below](#retired-agent-platforms)).
- **A redirect after sign-in** goes only to a path on the portal itself: control characters, `//` and backslashes in the `next` value are refused.

## Every request is authorized again

Nothing is cached between a client's list and its call. Every request to `/mcp/{slug}` checks the credential, the person or service account, the gateway and its team, the caller's access and its expiry, the capability's selection and availability (published and approved, or the team's own; not above the gateway's sensitivity ceiling; not past its sunset), the credential's tool scope, the gateway's curation, the minimum role, any approval rule and the rate limits. A refused call looks the same as a call to something that doesn't exist. Server-side checks are authoritative; the web app's permission gates only explain.

Tool annotations and model output are never used for authorization. Definitions that change on a published server leave the catalog until they're approved again.

## What servers receive

- The caller's own credential is **never** forwarded. Each call carries an ES256 identity token for that server only (`aud` = the server's URL), valid for 5 minutes, with keys rotating every 30 days and published at `/.well-known/jwks.json`. It starts off for a server registered with no authentication on a public host and on for internal hosts and the header and OAuth modes, and a team can change it for any server. It also goes with an editor's manual **Test connection**, for that editor and with the gateway `omp:test`, so that a server that refuses it shows up at Test; refresh and scheduled checks send none.
- Identity tokens issued since v0.4.0 carry no `act` claim: no call is made on a person's behalf by an external platform. A call to an additional (failover) endpoint gets a token whose audience is that endpoint's URL, never the primary's.
- A person's provider token goes only to a server whose requirement for that capability names that provider **and that the person allowed**, at the address (scheme, host and port) it had when they allowed it; never on lists, discovery, tests or health checks. Moving a server to another host, or making it require another provider, ends everyone's permission. Since v0.3.1 a provider can also have an [access list](#provider-access-and-narrower-tokens): a server it excludes receives nothing, on any call. The token still holds every scope the person granted that provider unless the provider is set to narrow tokens, so a server they allowed usually receives all of them.
- A server's stored credential value never follows a change of URL to another origin, for any part of it (headers, bearer, Basic or a query key): the edit is refused unless it enters every part's value again or removes the credential. A query-string key travels in the URL, which servers and proxies may log; the portal redacts it everywhere it handles it. The same rule covers the portal's OAuth client secret and a server's TLS client key: another origin never keeps them.
- **A person's own key** (each person's own key mode) goes only to the server it was entered for, at the origin it was entered for, and only on that person's calls. There is no fallback: a call with no usable key is refused with a link and nothing is forwarded. A service account is refused; scheduled health checks send nobody's key. See [Keys, client credentials and TLS](#keys-client-credentials-and-tls).
- **The portal's own OAuth token** (the portal's own OAuth client mode) is one token for every caller of that server, service accounts included, so the identity token and the call log are the only record of who called.
- **A shared service connection** (a provider account a team connects for its service accounts) delivers the team's provider token only to the service accounts assigned to it, only to destinations the team explicitly allowed, and only while the provider's access list allows the destination server's team. The connection lapses when the person who connected it is no longer a team owner or admin, or is suspended. See [Service connections](/docs/teams/service-connections).
- A person's token for an OAuth-protected server goes only to that server's URL, which must equal its metadata's `resource`, and to its own token and revocation endpoints.
- Header names `MCP-Gateway-Identity`, `MCP-Gateway-Provider` and `MCP-Gateway-Provider-Token` are reserved, so a team can't forge them with a static credential.

## Credentials at rest

- API keys, service account keys, automation tokens, provisioning tokens and OAuth tokens are stored only as HMAC-SHA256 digests under `API_KEY_PEPPER`; a key is shown once.
- Every part of a server's static credential (sealed on its own), additional endpoints' credentials, people's own keys for servers, the portal's own OAuth client secrets, servers' TLS client keys, client secrets, people's and shared connections' provider tokens, signing keys' private keys, PKCE verifiers, consent links, recorded call contents, webhook destinations' URLs and signing secrets, task state and approval previews are encrypted with AES-256-GCM under `ENCRYPTION_KEY`, each bound to its row.
- Secrets are never returned by the API (only "configured" and a short hint, or fingerprints for certificates), logged, audited, put in call records or health checks, or captured. Tests check this with sentinel values across responses, logs, the audit log, call records and recorded contents.

See [Secrets and key rotation](/docs/operate/secrets-and-key-rotation).

## Outbound connections

Every connection to an MCP server, an auth provider's token, revocation or userinfo endpoint, a client metadata document or an OAuth-protected server's metadata goes through one address guard: public addresses over https; internal ones only where a platform admin allowed them; never loopback, link-local (including cloud metadata), unspecified, multicast or broadcast, whatever the list says. Every resolved address is checked and the connection pinned to it (no DNS rebinding), redirects are never followed and proxy settings are ignored. See [Internal networks](/docs/administer/internal-networks).

**Webhooks** use the same guard but **not** the allowlist of internal networks: a team owner chooses a webhook's URL, and with that list a team owner could make the portal send requests into your network. Webhooks reach public https addresses only, unless the operator lists a network in `NOTIFY_WEBHOOK_ALLOWED_NETWORKS`. See [Notifications](/docs/administer/notifications).

## Consent links

A `-32042` consent link contains only an opaque ID: no personal data, and it signs nobody in. It works only in the browser session of the person whose call created it, once, for 10 minutes. The confirm page shows every scope before the provider is contacted. The OAuth `state` is bound to that session, person, provider and request (stopping login CSRF and mix-up), and redirects after the callback go only to same-origin paths.

## Approvals

**Catalog approvals.** A platform admin's approval of a server or capability names what the reviewer saw: the review dialog sends a digest of the server's definitions (or a capability's fingerprint), and an approval of something that changed in between is refused with `409 changed_since_review`. A team's own servers need no approval for the team's own gateways: review protects other teams.

**Sensitive-call approvals** (v0.5.0). An [approval rule](/docs/teams/approval-rules) makes a tool call wait for a person's decision. What the portal promises:

- **Exact call, single use.** An approval is bound to the merged arguments, the tool's definition and the caller. It authorizes one dispatch, within its validity (15 minutes by default); the call is never replayed automatically. A status of `used` means the authorization was spent, not that the server ran the call.
- **No self-approval.** The requester never decides their own request. The owners and admins of a requesting service account's team are excluded unless the rule allows it. Platform admins are a fallback only when nobody else is eligible; an empty set of reviewers refuses the call.
- **Fail closed.** Decisions take a table lock; when concurrent authority writes or maintenance hold it, a governed call is refused, not delayed.
- **Previews are private.** The argument preview is redacted (built-in rules, your patterns, known credential values, and every JSON-looking string masked), cut at 16 KiB, encrypted, and cleared within 24 hours of the request becoming final; metadata is kept 90 days. Platform admins and auditors see metadata, never a preview. Approval notices go to the inbox and email, never to webhooks.
- Governed calls use only a server's primary endpoint and are never run as MCP tasks.

Rules add a human gate; they never grant access a caller lacks. Session only: tokens can't manage rules or decide.

## Tool scopes and curation

A **tool scope** on a personal key, a service account or its key, a gateway grant or an OAuth grant (`omp:read`, `omp:write`, `omp:destructive`) is a ceiling, never a grant: it can only narrow what the caller's access already allows. No scope means unrestricted; an empty scope (`{}`) denies every tool. A scope matches a tool's owner-set class (read, write, destructive) or its exact exposed name, so an unclassified tool matches only by name. Every layer must match: the key, the account and the gateway grant. See [Tool scopes](/docs/use/tool-scopes).

**Curation** lets a gateway's owners rename a selected tool, rewrite its description and fix or narrow its arguments ([Curating gateway tools](/docs/teams/curating-gateway-tools)). The policy is bound to the tool's definition fingerprint: when the definition changes, the tool isn't served until an owner saves the policy again. Fixed and allowed values are enforced on every call, before consent, approval or forwarding. A rewritten description is text shown to the model, not a security control. Writing curation needs a browser session.

## Access requests and stewards

A platform gateway can be opted in to being discoverable, so people can request access ([Access requests](/docs/administer/access-requests)). Opting in shows the gateway's name and description to every active signed-in person. Named **stewards** decide that gateway's requests only: stewardship gives no MCP access, no editing and no direct grants. A requester never decides their own request, even as a platform admin or steward. Reasons and notes never reach the audit log, webhooks or notification payloads. Approved access is an ordinary grant, optionally expiring; expiry is enforced at the deadline, without waiting for cleanup.

## Upstream protection and failover

- **Quotas, caps and the breaker** protect a server from callers; they never expose another caller's counts ([Protection and failover](/docs/teams/protection-and-failover)).
- **Retries** happen only for read-class tools, `prompts/get` and `resources/read`, at most twice within the original timeout. Never for write, destructive, unclassified or governed calls, streams, or a send that may have reached the server.
- **Additional endpoints** have their own credentials, entered for each endpoint and bound to its origin; the primary's credential never goes to them. A write switches to another endpoint only when the first one positively never received it. Governed calls use the primary only. Reviewers see destinations and credential shape, never values.

## MCP Tasks

A task handle is a lookup key, not a credential. It is bound to the credential that started the task, and every `tasks/get`, `tasks/update` and `tasks/cancel` is authorized again against the current access, definition and curation. A handle for another credential, or one that no longer matches, is answered as "Task not found". Each lifecycle request is sent once, never retried. Cancelling a task doesn't prove the server stopped working. See [MCP Tasks](/docs/server-authors/tasks).

## Server governance

A gateway's **sensitivity ceiling** and a server's **sunset** are enforced at dispatch: a server above the ceiling, or past its sunset, is unavailable at that moment, also for a call that was listed earlier. Only team owners and admins confirm a sensitivity label; tokens can never change governance, ceilings or transfers. Nothing is unpublished, disabled or deleted automatically. See [Server governance](/docs/teams/server-governance).

## Provisioning (SCIM)

- **Linking is by identity, not by name.** A provisioned person links to a portal person only when its `externalId` equals their verified OpenID Connect subject. Email and `userName` never link accounts.
- **Protected roles.** Platform admins and team owners are never directory managed. Keep one unmanaged platform admin for break-glass access.
- **Deactivation** suspends the person at once and ends their browser sessions; in-flight requests can't mint keys. Credentials are kept. Deletion suspends, then cleans up sessions, grants, connections and keys.
- **Not covered:** the portal doesn't revoke tokens at providers when it cleans up, and signing out at the identity provider doesn't end portal sessions: only a SCIM deactivation or deletion does. See [Provisioning](/docs/administer/provisioning).

## Request epochs and session generations

Since v0.12.0, suspending a person fences requests already in flight (a key being created then fails with `409 request_authority_changed`), and a reactivated person's old browser sessions stay ended. Both hold only once every replica runs v0.12.0 or later.

## Retired: agent platforms

v0.3.0 to v0.3.2 let a trusted external agent platform name the person an agent acted for. v0.4.0 retired it (migration `00034`): trusted platforms and relay service accounts are disabled, their keys revoked, and inbound `MCP-Gateway-Identity` is refused with `403`. Historical call records keep their read-only attribution. The residual it carried (M-1 in the threat model) was **withdrawn** with the feature, not fixed in older releases: upgrading is the containment, and restoring a backup from before v0.4.0 restores the exposure. See [Agent platforms](/docs/administer/agent-platforms).

## Provider access and narrower tokens

Since v0.3.1 a platform admin can **restrict** an auth provider to listed teams and servers, so that other teams' servers can't require it or receive people's tokens. It is checked when a requirement is saved, when a person allows a server, and on **every call**: a server the list excludes gets `-32010` (`provider_not_allowed`), nothing is sent to it and no consent link is made. A provider created after the upgrade starts restricted; **providers that existed before stay open** to every team until an admin restricts them, and the admin pages flag them. Changing who may use a provider works only in a browser session, never with an automation token. See [Auth providers](/docs/administer/auth-providers#who-may-use-a-provider).

A provider can also be set to **narrow tokens per call**: a call carries a token refreshed with only the scopes it needs, kept in memory and never stored, and a provider that refuses the narrower scope fails the call instead of falling back to the full token. Only the Microsoft Entra ID preset pre-fills it, from Microsoft's documentation, not run against a live tenant. A provider that ignores `scope` on refresh returns its full token even with the switch on, and a connection with no refresh token is not narrowed. See [Narrower tokens per call](/docs/administer/auth-providers#narrower-tokens-per-call).

## Keys, client credentials and TLS

Since v0.3.2 a server can be reached with a **key each person pastes**, with the **portal's own OAuth client**, or over **mTLS with a private CA**, in any combination ([the five modes](/docs/teams/register-a-server#authentication-modes)). Each is a new place where a secret is held and a new place where an editor could try to send it. What the portal promises, and what it doesn't:

| Risk | What stops it | What remains |
|---|---|---|
| **An editor re-points a server to collect people's keys** (PS-1) | A key is bound to the origin it was entered for. Another origin, another mode, another placement or deleting the server deletes everyone's keys in the same transaction (audited), and every call refuses a key whose origin isn't the server's now. The paste page names the server, its team and the address. A published server goes back to review when the placement, name or prefix changes. An automation token can't switch the mode or send the settings | A person who pastes a key for a malicious server that review didn't stop hands it that key (theirs alone, for that server alone). A query placement puts the key in an address that servers and proxies may log |
| **A key is read back or leaks** (PS-2, PS-3) | No operation returns it, only its last four characters. The six operations are browser-session only, with no token scope. The bare key, the key with its prefix and their URL-encoded forms are redacted from errors, results, logs, audit entries, call records, recorded payloads, health messages and spans | Someone with the database **and** `ENCRYPTION_KEY` can read keys, as for every sealed value. A server that transforms a key before echoing it (a hash, another encoding) isn't recognised |
| **A call uses another person's key, the team's, or falls back to another credential** (PS-4) | The call reads the acting person's key only. With no usable key it is refused with the consent answer and nothing is forwarded. A service account is refused | None found |
| **A suspended or departed person's key keeps working** (PS-5) | A suspended person's calls are refused before the key is read, and their keys are kept; deleting the person deletes them; platform admins can remove anyone's key | A person removed at the identity provider but still active here keeps their keys working until they are suspended or removed |
| **A bad key is retried, or a robot uses a person's key** (PS-6, PS-7) | A `401` or `403` marks the key rejected and nothing is retried. Scheduled health checks send no key; Test and Refresh use only the key of the editor chosen for it, while they are an active editor and the key is active for the origin now | A `403` that is only a permission failure on one tool also asks for the key again. The setup editor's key is used for every Test and Refresh by any editor |
| **An editor sends the OAuth client secret, or the token it buys, to a place they control** (MO-1, MO-2) | A different token endpoint, client ID or server origin needs the secret entered again in the same request, and nothing is sent to the new place first. The token endpoint is checked against the address rules when saved and on every request, with no proxy and no redirects. Only an OAuth error code is ever kept from the authorization server. The secret and the token are redacted everywhere | An editor who knows the secret can move it. An allow-listed internal token endpoint is reachable by any editor, as for servers |
| **An automation token plants a secret, a CA or a mode** (MO-3, UM-3) | `personSecret`, `machineOAuth` and `tls`, and a switch into either secret mode, are browser-session only on create and update, even on a server with nothing stored | None found |
| **The portal's token is a shared credential** (MO-4) | The identity token (still signed per caller) and the call log say who called. A published server goes back to review for a new endpoint, client, scope, audience or resource, and the review digest covers them | A server that ignores the identity token can't tell callers apart. An authorization server that ignores `resource` and `audience` leaves the token usable at other servers that trust it. A revoked token is used until the server answers `401` or it expires |
| **A storm of token requests** (MO-5) | One token per server in memory, shared by concurrent callers; a `401` renews once and retries the call once; an unavailable token endpoint fails the call fast | A server that rejects every fresh token costs one token request per call until it is fixed (`omp_machine_token_requests_total` shows it) |
| **A server's TLS settings weaken its verification, leak the client key or let a trust change through** (UP-8) | There is no way to skip verification anywhere in the product, the URL's host name is always checked, and TLS 1.2 is the minimum. A server's CA replaces the system roots for that server only. The key is sealed with a binding to the server and the field, and never returned, logged, audited or put in an error. A key and CA never follow a URL to another origin. A changed or removed CA sends a published server back to review; the digest covers both fingerprints. Expiry is surfaced 14 days ahead. The address rules are unchanged: TLS runs over the connection the guard pinned | A bad CA uploaded by a team editor weakens that server's own TLS: an on-path attacker could read the identity token and any header or token sent to it. Review covers other teams, not the team itself, and under **Self-publish** there is no review. The client key is a long-lived secret in the database, so it is in backups. A client certificate is presented to whatever the server's CA vouches for. No revocation checking (CRL, OCSP) |
| **A secret of a mode the server left stays, or goes to the next mode** (UM-1, UM-2) | Leaving a mode deletes its secrets in the same transaction as the switch. Another origin discards every kind of secret unless the same request replaces it | A static part is sent in every mode that allows one: it is the team's, not a mode's |
| **A secret leaks together with the others** (UM-5) | Every kind joins the call's redaction and the key rotation | A team's static credential echoed back by its own server reaches the caller in the tool result (it is redacted from logs, error messages and recorded payloads) |
| **A token endpoint or sign-in metadata behind a private CA is trusted with the server's CA** (UM-6) | The TLS settings are for the MCP server's URL only: the token request and discovery use the system roots and no client certificate | A server in OAuth mode, or one using the portal's OAuth client, whose authorization server uses a private CA isn't supported |

The IDs are the rows of the repository's [threat model](https://github.com/ncecere/open-mcp-portal/blob/v0.13.1/docs/threat-model.md) (sections 6.10 to 6.12 and UP-8), with the tests that cover each.

**Hardening when you use them:**

- **Prefer a header or a bearer token over a query key** for people's own keys, and a header over a query part for a static credential.
- **Read the TLS card when you review a server that has one** (fingerprints, subjects, expiry). Under **Self-publish** no one reviews a team's CA change.
- **Keep a client certificate narrow**: scope what the key can reach on the server to what the portal needs, and rotate it when someone who could read the database leaves, since backups hold the sealed key.
- **Set the `resource` or `audience` your authorization server supports** on the portal's OAuth client, so the token isn't usable elsewhere, and give the client only the scopes the server needs. Use it only where sharing the portal's token among all callers is acceptable.
- **Watch `omp_machine_token_requests_total{result="refused"}`** ([Metrics](/docs/operate/metrics)) and the expiring-certificate warnings on the overview.
- **Restrict who can edit servers.** Editors choose where keys and secrets go; the review gate covers other teams, not a team's own gateways.

## Telemetry

Tracing is off unless an OTLP endpoint is configured ([Tracing](/docs/operate/tracing)). When it is on:

- **Spans carry only a fixed allow-list of attributes** (slugs, outcome, principal kind, classes, status): never a person, an email, a key, a tool or prompt name, arguments, results, headers, paths, addresses or tokens. Errors are a class, never text. A test scans every span of a call made with sentinel secrets.
- **The export headers are a secret** (`_FILE` works), never logged or shown by `doctor`. Over `http://` they and the spans cross the network in clear text: use https outside the cluster.
- **A sampled call sends its trace context to every MCP server it calls, third-party ones included.** A trace id is not sensitive, but a third party can correlate calls that carry the same id. `baggage` is passed only as the client sent it.
- **A client can ask for its request to be traced** with a sampled `traceparent` when the sampler is parent-based (the default). The cost is bounded; use `traceidratio` if untrusted clients can reach the portal.
- **Trace ids are identifiers, not personal data.** They are kept on call records (deleted with the call by retention) and in logs of sampled requests. The trace backend's own retention is separate, and it sees your gateway, server and provider slugs and must be trusted like your logs.

## Records

The audit log and call records are append-only (database triggers refuse changes; only the retention job deletes, past their periods). With [separate database logins](/docs/operate/database-roles), the runtime login can't update or delete them at all, and retention deletes them only through owner functions that keep at least 30 days of audit and 1 day of call records. That protects recent history against a leaked runtime credential; it doesn't make history tamper-proof against the owner. Every change is audited in the same transaction. Recording of call contents is off by default, redacted, truncated, encrypted, readable only by the recording team's owners and admins and by platform staff, and every view is audited.

## Deployment

- `serve` refuses the example keys, development sign-in and an http `APP_URL` off loopback.
- The image is distroless and runs as a non-root user with a read-only filesystem; the Kubernetes base meets the `restricted` Pod Security Standard and ships default-deny NetworkPolicies.
- The metrics listener has no authentication: keep it on a separate port reachable only by monitoring.
- With tracing on, allow egress only to your collector (the example overlay has an OTLP egress policy).
- Put the ingress's own rate limits in front of unauthenticated traffic.

## Hardening status

The repository's [threat model](https://github.com/ncecere/open-mcp-portal/blob/v0.13.1/docs/threat-model.md#9-hardening-ideas-not-findings) keeps a list of hardening ideas, numbered H-1 onward, which are suggestions rather than known vulnerabilities, and a table of where each stands (reviewed 2026-10-18, for v0.2.1, and updated since). v0.2.2 closed most of them, v0.3.0 finished one more detail (H-7's old cookie name), and v0.3.1 closed H-5 except the items in its row below. v0.3.3 closed H-12 and v0.4.0 built H-11. The agent-platform residual M-1 was withdrawn with the feature in v0.4.0 ([Retired: agent platforms](#retired-agent-platforms)).

| Idea | Status in v0.13.1 | What remains |
|---|---|---|
| **H-1**, trusted clients and loopback redirects | **Partly done** (decision 62) | A trusted client's first sign-in to a gateway with a loopback redirect asks once ([Trusted clients](/docs/administer/trusted-clients#the-first-sign-in-from-this-computer)). After that first confirmation a local process can still use the trusted client's ID silently, and a process that drives the person's browser can press Continue. What limits it: the person must be signed in in their browser, the code is PKCE-bound and the token is bound to one gateway |
| **H-2**, `sendIdentity` default | **Mostly addressed** (decision 64) | The default is off for a server with no authentication on a public host, on for internal hosts and other modes; an explicit value is kept and existing servers are unchanged ([Send identity token](/docs/teams/register-a-server#send-identity-token)). A manual Test sends the token and diagnoses a `401` or `403`. A server that accepts the request and refuses only when a tool runs (DeepWiki's public endpoint) still passes Test; each call's record shows whether the token was sent. Servers registered before v0.2.2 keep their value |
| **H-3**, anonymous client-metadata fetch | **Done** | An anonymous request is sent to sign in before the app is looked at (no fetch, no reason), and uncached fetches are limited to 20 a minute per address. A signed-in person can still make the portal fetch guarded public URLs up to the cap, and the address is shared behind an ingress without `TRUSTED_PROXIES` |
| **H-4**, open client registration | **Done except two accepted gaps** (the cap in v0.2.1, the controls in v0.2.2) | `OAUTH_MAX_REGISTERED_CLIENTS`, an admin switch that turns registration off, a 24-hour life for registrations that never received tokens, `OAUTH_MAX_UNUSED_CLIENTS_PER_ADDRESS` (20) and a `doctor` line ([Configuration](/docs/operate/configuration#oauth-clients)). The per-address cap counts only unused registrations (and is one shared address behind an ingress without `TRUSTED_PROXIES`), many addresses can still fill the global cap, and there is no browser-only check, which would break native apps |
| **H-5**, per-provider allow-list and per-call scopes | **Done in v0.3.1 (decision 69), with residuals** | A per-provider access list (open or restricted; checked on saving a requirement, on allowing a server and on every call) and narrower tokens per call ([Auth providers](/docs/administer/auth-providers#who-may-use-a-provider)). Remaining: providers left open are unchanged until an admin restricts them; narrowing is only as real as the provider's support for `scope` on refresh (only Microsoft is pre-filled, from its documentation, not run against a live tenant), and a connection with no refresh token isn't narrowed; one token per person, provider and server, several accounts per provider and RFC 8693 token exchange are not built; an OAuth-mode server that links a platform provider's client isn't gated by the list (it shares the client, never the connections). The other half of H-5, a body read deadline on unauthenticated POSTs, is partly done: the header and idle timeouts are set, and per-handler body deadlines are not |
| **H-6**, upstream error text relayed | **Reviewed, kept** | It is capped at 300 characters and redacted, and it proved useful: DeepWiki's own message told the person what was wrong |
| **H-7**, proxy and cookie checks | **Done, with residuals** | `ENCRYPTION_KEY` and `API_KEY_PEPPER` must differ; the sign-in state cookie is `__Host-` prefixed on https; a once-a-minute warning and a `doctor` line when `TRUSTED_PROXIES` is empty behind a proxy ([Behind a proxy](/docs/operate/configuration#behind-a-proxy-trusted_proxies)). The old cookie name was accepted in v0.2.2 and is no longer read since v0.3.0; there is no warning for a `TRUSTED_PROXIES` that is set but wrong |
| **H-8**, refresh token lifetime | **Done** (decision 63) | `OAUTH_REFRESH_ABSOLUTE_TTL` (180 days, `0` for none) from the last sign-in; a repeat inside the 30-second grace gets the same pair. A leaver's grants last up to the lifetime unless someone disconnects them or suspends the person |
| **H-9**, image and scan hardening | **Done, with a residual** | `govulncheck` and `npm audit` block CI; Trivy fails the release on fixable high and critical findings; the Dockerfile's base images are pinned by digest. Digests are current only as far as Dependabot's weekly pull request is merged |
| **H-10**, off-host audit export | **Open** | Needs a destination. The audit log is append-only and exportable as CSV |
| **H-11**, split database roles | **Done, opt-in** (v0.4.0) | Separate migration and runtime logins, least-privilege grants reconciled by `migrate`, owner-only purge functions with fixed age floors, and a `doctor` check ([Database roles](/docs/operate/database-roles)). The default single-login setup only warns. The floors don't make runtime-writable settings or usage rollups trustworthy |
| **H-12**, idle timeout and session list | **Done** (v0.3.3, decision 76) | `SESSION_IDLE_TIMEOUT` (off by default, 5 minutes up to `SESSION_TTL`); people list and end their sessions, and platform admins end a person's. Activity is recorded at most once a minute. Connected apps and keys are separate |

v0.2.2 added an end-to-end test that a provider token a server echoes back is redacted from recorded payloads, audit, call records and logs. The repository's table is the full record; this page summarises it.

## What the portal doesn't do

- It doesn't check that a person's provider account is theirs (for example by email).
- It doesn't vet what an MCP server does with a call it was allowed to receive, or defend against prompt injection in tool results.
- Redaction catches common secret formats and your patterns, not everything.

## Reporting a vulnerability

Report vulnerabilities privately through the repository's [security advisories](https://github.com/ncecere/open-mcp-portal/security/advisories/new), as its `SECURITY.md` describes. Don't open a public issue.
