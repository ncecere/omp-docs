## The image

Each release publishes a multi-arch (linux/amd64, linux/arm64) image to GitHub's container registry, tagged with the release:

```sh
docker pull ghcr.io/ncecere/open-mcp-portal:v0.13.1
docker run --rm ghcr.io/ncecere/open-mcp-portal:v0.13.1 version     # open-mcp-portal 0.13.1 (<commit>)
```

The digest of the v0.13.1 image is:

```text
sha256:cec6a9e1189845ca2f9827e972c55af20ce22de3a40645abdf3ab08a6730a453
```

The image is scanned for known vulnerabilities before it is published, carries an SBOM and build provenance, and is signed with cosign keyless signing by the repository's `image.yml` workflow. Check the signature (use **cosign v3.0 or newer**) before you use it:

```sh
cosign verify ghcr.io/ncecere/open-mcp-portal@sha256:cec6a9e1189845ca2f9827e972c55af20ce22de3a40645abdf3ab08a6730a453 \
  --certificate-identity https://github.com/ncecere/open-mcp-portal/.github/workflows/image.yml@refs/tags/v0.13.1 \
  --certificate-oidc-issuer https://token.actions.githubusercontent.com
```

Then pin the image by that digest (`ghcr.io/ncecere/open-mcp-portal@sha256:cec6a9e1189845ca2f9827e972c55af20ce22de3a40645abdf3ab08a6730a453`) in your Compose file, so a moved tag can't change what you run. `docker buildx imagetools inspect ghcr.io/ncecere/open-mcp-portal:v0.13.1` shows the digest a tag points to now; compare it with the one above.

To build the image yourself instead, from a checkout of the tag:

```sh
git clone --branch v0.13.1 https://github.com/ncecere/open-mcp-portal
cd open-mcp-portal
make docker                         # open-mcp-portal:<git describe>
make docker-omp                     # omp-cli:<git describe>, the omp command line (docker build --target omp)
```

No image is published for the `omp` command line; each release attaches signed binaries instead ([The omp command line](/docs/api/cli#install)).

- The image is distroless: the binary is `/open-mcp-portal` (the entrypoint) and there is no shell. Commands: `serve` (default), `migrate`, `doctor`, `rotate-keys`, `version`.
- It runs as UID/GID 65532, listens on port 8088 (`LISTEN_ADDR`) and needs no writable filesystem.
- There's no `HEALTHCHECK` (no shell or curl): probe `/healthz` and `/readyz` from your orchestrator.
- Multi-arch: `docker buildx build --platform linux/amd64,linux/arm64 --build-arg VERSION=… --build-arg COMMIT=… .` The web app and Go builds run on the build platform and cross-compile.

## The demo

`make demo` (`docker compose -f compose.demo.yaml up --build`) runs the portal, PostgreSQL and a fake MCP server with development sign-in on [http://localhost:8090](http://localhost:8090). It is for trying things on your own machine only. See [Try it locally](/docs/get-started/try-it-locally).

## A single instance

The repository has no production Compose file. For a small install, write your own along these lines: the portal and PostgreSQL 17, with TLS terminated by a reverse proxy you already run in front of port 8088.

```yaml
services:
  postgres:
    image: postgres:17
    environment:
      POSTGRES_USER: omp
      POSTGRES_DB: omp
      POSTGRES_PASSWORD_FILE: /run/secrets/postgres-password
    secrets: [postgres-password]
    volumes: [postgres:/var/lib/postgresql/data]
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U omp -d omp"]
      interval: 5s
      retries: 30

  portal:
    image: ghcr.io/ncecere/open-mcp-portal@sha256:cec6a9e1189845ca2f9827e972c55af20ce22de3a40645abdf3ab08a6730a453   # v0.13.1
    command: ["serve"]
    depends_on:
      postgres:
        condition: service_healthy
    environment:
      APP_URL: https://mcp.example.com
      LISTEN_ADDR: :8088
      MIGRATE_ON_START: "true"          # fine for one instance; see Migrations
      OIDC_ISSUER: https://idp.example.com
      OIDC_CLIENT_ID: open-mcp-portal
      # Optional, for notification email (off without SMTP_HOST); see Configuration:
      # SMTP_HOST: smtp.example.com
      # SMTP_FROM: Open MCP Portal <portal@example.com>
      BOOTSTRAP_ADMIN_SUBJECT: "<the first admin's OIDC sub>"
      TRUSTED_PROXIES: 172.16.0.0/12    # your reverse proxy's addresses
      DATABASE_URL_FILE: /run/secrets/database-url
      ENCRYPTION_KEY_FILE: /run/secrets/encryption-key
      API_KEY_PEPPER_FILE: /run/secrets/api-key-pepper
      OIDC_CLIENT_SECRET_FILE: /run/secrets/oidc-client-secret
    secrets: [database-url, encryption-key, api-key-pepper, oidc-client-secret]
    ports: ["127.0.0.1:8088:8088"]
    read_only: true
    restart: unless-stopped

secrets:
  postgres-password: { file: ./secrets/postgres-password }
  database-url: { file: ./secrets/database-url }        # postgres://omp:<password>@postgres:5432/omp?sslmode=disable
  encryption-key: { file: ./secrets/encryption-key }    # openssl rand -base64 32
  api-key-pepper: { file: ./secrets/api-key-pepper }    # openssl rand -base64 32 (a different value)
  oidc-client-secret: { file: ./secrets/oidc-client-secret }

volumes:
  postgres: {}
```

Then:

1. Register `https://mcp.example.com/auth/callback` as the redirect URI of the portal's client at your identity provider.
2. Point your reverse proxy's host at port 8088, with read timeouts of a few minutes (a call can wait up to 120 seconds for its MCP server), request bodies of at least 1 MiB, and **response buffering off**: a call that asks for progress is answered as a stream of server-sent events, which a buffering proxy holds back (see [Ingress](/docs/operate/kubernetes#ingress) for the settings per proxy). Route every path to the portal, including `/mcp/`, `/oauth/`, `/connect/`, `/scim/` and `/.well-known/`.
3. `docker compose up -d`, then `docker compose exec portal /open-mcp-portal doctor` to check everything.
4. Sign in as the bootstrap admin and follow [First run](/docs/administer/first-run).

Every setting is in [Configuration](/docs/operate/configuration). Keep the encryption key and pepper somewhere safe besides the server: see [Backups](/docs/operate/backups).

### Separate database logins

The file above runs the portal as the database owner, which is the single-owner setup. To keep the owner credential out of the serving container, create two PostgreSQL logins ([Database roles](/docs/operate/database-roles#set-it-up-on-a-new-database)) and change the file:

- Point `database-url` at the **runtime** login (`omp_app`) and set `MIGRATE_ON_START: "false"` and `DB_REQUIRE_SPLIT_ROLES: "true"` on `portal`.
- Put the **owner** URL (`omp_owner`) in a second secret file that only the migration run mounts, and run it once before each upgrade:

```sh
docker compose run --rm \
  -e DATABASE_MIGRATE_URL_FILE=/run/secrets/database-migrate-url \
  -e DB_RUNTIME_ROLE=omp_app \
  -v "$PWD/secrets/database-migrate-url:/run/secrets/database-migrate-url:ro" \
  portal migrate
```

`migrate` uses `DATABASE_MIGRATE_URL` and then grants the runtime role what it needs. Don't list the owner secret under the `portal` service.

<Callout type="warn" title="Never reuse the demo's settings">
Off a loopback `APP_URL`, `serve` refuses to start with the example `ENCRYPTION_KEY` or `API_KEY_PEPPER` from `.env.example`, with `DEV_AUTH=true`, or with an `http://` `APP_URL`.
</Callout>
