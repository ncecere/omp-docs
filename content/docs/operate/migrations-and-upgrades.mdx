description: How Open MCP Portal applies its forward-only database migrations, and how to upgrade and roll back safely.

## Migrations

The database schema is managed by migrations built into the binary. They are **forward-only and expand/contract**: a release's migrations keep working with the previous release's code, so a rolling upgrade never breaks the replicas still running the old version.

- In Kubernetes, the `migrate` init container runs `open-mcp-portal migrate` in every new pod. A PostgreSQL advisory lock serialises concurrent runs, so only the first pod does any work.
- Elsewhere, run `open-mcp-portal migrate` before starting `serve`, or set `MIGRATE_ON_START=true` on a **single** instance.
- `serve` refuses to start while migrations are pending; the message names the current and required versions. `doctor` reports the migration state too.

`migrate` needs only `DATABASE_URL`.

## Upgrading

1. **Read the release notes** of every release between yours and the target. See [Releases](/docs/releases).
2. **Back up** the database. See [Backups](/docs/operate/backups).
3. **Pin the new image**, by digest.
4. **Migrate, then roll.** In Kubernetes, the new pods' `migrate` init container applies the schema before any new pod serves, while the old pods keep serving (`maxUnavailable: 0`). Elsewhere, run `migrate` with the new image first, then restart `serve`.
5. Run `doctor`.

## Rolling back

Pin the previous image. Migrations are never rolled back automatically; because they are expand-only, the previous release normally runs on the newer schema. To undo a migration itself, restore the backup made before the upgrade. **Don't use `goose down`** to go back past `00026`, `00025` or `00024` (v0.3.2), `00023` (v0.3.1) or `00020` (v0.3.0): it would drop people's own keys for servers, the portal's OAuth clients and the TLS settings with their sealed keys, the provider access lists, the stored credential parts, the call records' trace ids, the trusted agent platforms, the relay marks and the agent columns of the call history. Pin the previous image instead. One thing a rollback to v0.3.0 does change: it ignores the credential parts table, so a server whose credential was saved as a list reads as having no credential until you save it as one header again (see [Upgrading from v0.3.0](#upgrading-from-v030)). A rollback to v0.3.1 does the same for the new modes: it ignores the new tables, so a server in each person's own key mode reads as one with no credential, a server in the portal's own OAuth client mode reads as one without authentication, and the TLS settings aren't used (see [Upgrading from v0.3.1](#upgrading-from-v031)).

## Upgrading from v0.3.1

v0.3.2 adds migrations `00024`, `00025` and `00026`. All three are **expand-only**: they add tables, nullable columns and a widened check, and a server that doesn't use a new mode is read the same by v0.3.1, so the steps above apply and a rolling upgrade is safe. The release's own summary is in the [v0.3.2 notes](/docs/releases/v0-3-2#upgrading). **Nothing changes for existing servers**: each new feature is something a team opts into on a server. Coming from v0.3.0 or earlier, read [Upgrading from v0.3.0](#upgrading-from-v030) too.

- **Migrations.** `00024` adds the tables for people's own keys and the links that ask for them, some nullable columns and the `person_secret` mode. `00025` adds the table that holds the portal's own OAuth client for a server and the `machine_oauth` mode. `00026` adds the table for a server's TLS settings. The `migrate` init container, or `migrate` run once before `serve`, applies them.
- **Put servers in a new mode only after every replica runs v0.3.2.** The previous image ignores the new tables. Until then it reads a server in each person's own key mode as one with no credential and a server in the portal's own OAuth client mode as one without authentication.
- **No rolling back with `goose down` once a server uses a new mode.** Pin the previous image instead (see [Rolling back](#rolling-back)). What the down migrations do: the one for `00024` and the one for `00025` each remove only their own mode from the allowed modes and never fail because servers of another mode exist. A server in the removed mode goes back to `static_header` if it still has a static credential of its own, else to `none`, and the secrets of the removed mode go with their tables. That is why a rollback is a pinned image, not a migration.
- **The two mode migrations are order-independent.** `00024` and `00025` both rewrite the database's list of allowed authentication modes. Applied naively, the later one would have dropped the earlier one's value; each now adds its value to whatever the list holds, and a test applies them in both orders and twice.
- **One `409 changed_since_review`.** A published server's review request that is open during the upgrade gets one `409 changed_since_review` when the reviewer approves, because the review digest (now `omp-review-v3`) also covers the CA and client-certificate fingerprints, the placement of a person's key and the portal's OAuth client. The reviewer reloads and approves again.
- **`error_class` is no longer an enumerated list.** Migration `00026` replaces the database check on a health check's `error_class` with a length bound, so a new class needs no migration. The new class `tls` is used for certificate and handshake problems; the API's `McpErrorClass` gains it, and a script that matches on error classes should expect new ones.
- **Key rotation covers the new secrets.** `rotate-keys` re-seals people's own keys, the key-entry links, the portal's OAuth client secrets and the TLS client keys with the other sealed values; `ENCRYPTION_KEY` is the only secret that protects them ([Secrets and key rotation](/docs/operate/secrets-and-key-rotation)).
- **No new setting or environment variable.** A new metric, `omp_machine_token_requests_total`, counts token requests of servers that use the portal's own OAuth client ([Metrics](/docs/operate/metrics)).
- **Run `doctor`** as usual after the upgrade.

## Upgrading from v0.3.0

v0.3.1 adds migrations `00021`, `00022` and `00023`. All three are **expand-only**: they add tables and nullable columns and change nothing that v0.3.0 reads, so the steps above apply and a rolling upgrade is safe. The release's own summary is in the [v0.3.1 notes](/docs/releases/v0-3-1#upgrading). **Nothing changes for existing providers or servers until an admin opts in**, except that credentials you save from now on may be stored in the new form.

- **Migrations.** `00021` adds the auth providers' access lists and the narrowing switch, `00022` the table that holds a server's credential parts, and `00023` a nullable trace id on call records. The `migrate` init container, or `migrate` run once before `serve`, applies them. Because they only add tables or nullable columns, the previous image keeps working against the new schema.
- **No rolling back with `goose down`.** Pin the previous image instead (see [Rolling back](#rolling-back)). v0.3.0 reads a server whose credential was saved as parts (the new table) as having no credential, so before going back, save such a server's credential as one header again, or accept that it loses its credential until you do.
- **Existing auth providers stay open to every team.** Every provider that exists at the upgrade keeps working as before and is flagged in Admin › Auth providers (an **Open to every team** badge, and a warning on its **Access** tab). Decide which to restrict: Admin › Auth providers › the provider › **Access**. **A provider you create after the upgrade starts restricted** with nobody listed, so a team that expects to use it must be listed before it can require it. See [Auth providers](/docs/administer/auth-providers#who-may-use-a-provider).
- **One `409 changed_since_review`.** A published server's review request that is open during the upgrade gets one `409 changed_since_review` when the reviewer approves, because the review digest now covers the kind and name of each credential part (the digest version changed). The reviewer reloads and approves again.
- **Narrowing and background refresh are off.** Only the Microsoft Entra ID preset pre-fills **Narrow tokens per call**, for providers you add; existing providers are unchanged. `PROVIDER_REFRESH_INTERVAL` is `0` (off) until you set it.
- **Tracing is off.** It needs an OTLP endpoint ([Tracing](/docs/operate/tracing)). If untrusted clients can reach the portal, use `traceidratio` sampling: the default parent-based sampler lets a client ask for a trace by sending a sampled `traceparent`.
- **The binary is about 3.6 MB larger.** The OpenTelemetry exporter pulls in protobuf and gRPC packages.
- **Run `doctor`** as usual after the upgrade. It now also reports whether tracing is on.

## Upgrading from v0.2.2

Coming from v0.2.2, follow this section and then [Upgrading from v0.3.0](#upgrading-from-v030). v0.3.0 adds migration `00020`, which is **expand-only**: it adds tables and columns and changes nothing that v0.2.2 reads, so the steps above apply and a rolling upgrade is safe. The release's own summary is in the [v0.3.0 notes](/docs/releases/v0-3-0#upgrading).

- **Migration `00020`.** It adds the tables for trusted agent platforms and for the token IDs the portal has accepted, a relay mark on service accounts, the present-person settings of servers and capabilities, and the agent columns of the call history. The `migrate` init container, or `migrate` run once before `serve`, applies it. It takes no long lock on the call history, so a large `mcp_calls` table doesn't block calls while it runs.
- **No rolling back with `goose down`.** Undoing `00020` would drop the trusted platforms, the relay marks and the agent columns of the call history. Pin the previous image instead: v0.2.2 ignores the new tables and columns and keeps working against the new schema (see [Rolling back](#rolling-back)).
- **Nothing changes until it is configured.** The new surfaces are off until a platform admin adds a trusted platform and marks a relay service account. No setting or environment variable is new. To use it with Pi Durable Platform, follow [Agent platforms](/docs/administer/agent-platforms); the platform's `identityAudience` must be the portal's `APP_URL`.
- **The old sign-in cookie name is no longer read.** On https only `__Host-omp_oidc_state` is accepted, as v0.2.2 announced. A person who started signing in just before the upgrade starts again.
- **Run `doctor`** as usual after the upgrade.

## Upgrading from v0.2.1

Coming from v0.2.1, follow this section and then [Upgrading from v0.2.2](#upgrading-from-v022). v0.2.2 adds migrations `00018` and `00019`. Both are **expand-only** (they add columns and tables and change nothing that v0.2.1 reads), so the steps above apply and a rolling upgrade is safe. The release's own summary is in the [v0.2.2 notes](/docs/releases/v0-2-2#upgrading).

- **Migrations.** `00018` adds what the OAuth hardening needs (when each app was last signed in, the registration switch, and when and from where each registered client was created). `00019` adds a nullable column to call records that says whether the identity token was sent. The `migrate` init container, or `migrate` run once before `serve`, applies them.
- **Rolling back.** Pin the previous image: v0.2.1 ignores the new columns and keeps working against the new schema. Nothing is undone in the database (see [Rolling back](#rolling-back)).

Three behaviour changes to know before you upgrade:

1. **OAuth apps sign in again about every 180 days.** `OAUTH_REFRESH_ABSOLUTE_TTL` (default `180d`) counts from the person's last sign-in of the app. Apps connected when `00018` runs get one whole window from that moment, however old their grant is, so the upgrade signs nobody out. Set `OAUTH_REFRESH_ABSOLUTE_TTL=0` to keep the old unlimited life. API keys and service-account keys aren't affected: use them for agents that run without a person. See [Configuration](/docs/operate/configuration#oauth-clients) and [Connected apps](/docs/use/connected-apps).
2. **People who sign a trusted client in from their own computer see a one-time notice.** The first time a person signs a trusted client such as Claude Code in to a gateway through a `localhost` redirect, the sign-in page shows a short notice with **Continue** or **Cancel**. People who already connected the client aren't asked, and trusted clients with `https` redirects are unaffected. See [Trusted clients](/docs/administer/trusted-clients#the-first-sign-in-from-this-computer).
3. **New servers on public hosts with no authentication send no identity token by default.** A server registered with no authentication on a public host (or a name that can't be resolved) now starts with **Send identity token** off; internal hosts and the header and OAuth modes start on. Servers you already registered are unchanged. If a new public server expects the token, turn the switch on. See [Send identity token](/docs/teams/register-a-server#send-identity-token).

Also:

- Registrations that never received tokens are deleted after 24 hours, and one source address can hold `OAUTH_MAX_UNUSED_CLIENTS_PER_ADDRESS` (default 20) of them. Apps that were ever authorized are unaffected.
- An anonymous request to `/oauth/authorize` is sent to sign in before the app is looked at, so a person with a bad client learns it after signing in.
- On https the sign-in state cookie is now `__Host-omp_oidc_state`. The old name was still accepted in v0.2.2, so nobody who was mid sign-in during that upgrade was sent back; v0.3.0 no longer reads it.
- Behind a proxy, set `TRUSTED_PROXIES` if you haven't: with it empty, the portal logs a warning and `doctor` prints an info line ([Configuration](/docs/operate/configuration#behind-a-proxy-trusted_proxies)).

## Upgrading from v0.2.0

Coming from v0.2.0, follow this section and then [Upgrading from v0.2.1](#upgrading-from-v021). v0.2.1 has no migrations, and nothing you must change. The steps above apply; the release's own summary is in the [v0.2.1 notes](/docs/releases/v0-2-1#upgrading). Three points to know:

- **Open client registration is capped.** `OAUTH_MAX_REGISTERED_CLIENTS` (default `1000`, `0` for no cap) bounds the OAuth clients registered through `POST /oauth/register` that were used in the last 30 days. If more than that registered themselves in the last 30 days, new registrations get `503 temporarily_unavailable` until some go unused or you raise the setting. Most installs are nowhere near it. Clients that use a metadata document, such as Claude Code, aren't counted. See [Configuration](/docs/operate/configuration#oauth-clients).
- **Test connection sends the editor's identity token.** Editors who press it now cause the server to receive their identity token (name, email, team slugs), as real calls from them already do. Turn **Send identity token** off for a server that shouldn't receive it ([Send identity token](/docs/teams/register-a-server#send-identity-token)).
- **The Kubernetes manifests have a smoke test.** `make k8s-smoke` ([Smoke test](/docs/operate/kubernetes#smoke-test)) needs a checkout of the repository; it creates its own throwaway `kind` cluster and never touches `~/.kube`.

## Upgrading from v0.1.0

v0.2.0 adds migrations `00014` to `00017` (notifications, automation tokens, the protocol a server last negotiated, and per-server consent for provider tokens). The steps above apply; these are the points specific to this upgrade. The release's own summary is in the [v0.2.0 notes](/docs/releases/v0-2-0#upgrading).

<Steps>
<Step>

### Check your keys

The portal now refuses to start with an `ENCRYPTION_KEY` equal to the `API_KEY_PEPPER`, on any `APP_URL`. If an install used one value for both, give each its own, following [Secrets and key rotation](/docs/operate/secrets-and-key-rotation).

</Step>
<Step>

### Migrate, then roll every replica

Back up, pin the digest of the current release, v0.3.2, which includes v0.2.0's migrations and adds `00018` to `00026` (see [Install with Docker Compose](/docs/operate/compose#the-image) or [Install on Kubernetes](/docs/operate/kubernetes#the-image)), and run `migrate` once (the `migrate` init container, or `MIGRATE_ON_START` on a single instance). Then start **every** replica on v0.3.2 (at least v0.2.0). Read [Upgrading from v0.2.1](#upgrading-from-v021), [Upgrading from v0.2.2](#upgrading-from-v022), [Upgrading from v0.3.0](#upgrading-from-v030) and [Upgrading from v0.3.1](#upgrading-from-v031) too.

</Step>
<Step>

### Create no automation token until every replica runs v0.2.0

An older replica doesn't know the new `ompadm_` and `omppub_` prefixes, and can't list audit entries written by a token. Once every replica is on v0.2.0, platform admins and team admins can create tokens: see [Automation tokens](/docs/administer/automation-tokens) and [Publisher tokens](/docs/teams/publisher-tokens). `API_KEY_PEPPER_PREVIOUS` covers tokens too, so a pepper rotation keeps them working.

</Step>
<Step>

### Set up what you want, all optional

- **Email:** `SMTP_*` ([Configuration](/docs/operate/configuration#notifications)). Add the SMTP port to the NetworkPolicy's egress in Kubernetes.
- **Webhooks to internal receivers:** `NOTIFY_WEBHOOK_ALLOWED_NETWORKS`, and an egress rule for their port.
- **Streaming:** check that your ingress doesn't buffer or cut quiet responses ([Ingress](/docs/operate/kubernetes#ingress)).

</Step>
<Step>

### Tell people and script owners

- **Email needs one sign-in.** Email goes only to addresses the identity provider reported as verified, recorded at each sign-in. Until a person signs in after the upgrade they get notifications in the portal but no email.
- **One consent per server.** The first time a person calls a tool that uses a connected account after the upgrade, they allow that server once ([Connecting accounts](/docs/use/connecting-accounts#allowing-a-server)). There is no backfill, on purpose. A consent link issued before the upgrade is refused as expired: running the tool again makes a new one.
- **Scripts that approve must send the digest.** Anything that approves a server or a capability through the management API must send `expectedDigest` or `expectedFingerprint` ([Publishing and review](/docs/teams/publishing#approvals-name-what-was-reviewed)).

</Step>
<Step>

### Run `doctor`

`open-mcp-portal doctor` now also reports email and webhooks under `notifications`.

</Step>
</Steps>

Going back to v0.1.0 after you created automation tokens leaves audit entries that v0.1.0 can't list. Restore the backup from before the upgrade if you need to go back past a migration.
