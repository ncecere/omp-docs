Under the **Approval required** policy, platform admins decide what reaches the company catalog. **Admin › MCP servers** lists every team's servers; servers waiting for review come first, under **Waiting for approval**. Filter by state, pending changes, team, auth mode or the auth provider a server requires. Auditors see the same pages, read-only.

## Review a server

Open a server to see its **Overview** (URL, health, auth mode, the team's note and the publishing history), its **Capabilities** with their full definitions and hints, and its **Health**. Things to look at:

- **The capabilities' text.** Names, descriptions and schemas are prompts a model will read. Look for instructions aimed at the model, and treat the server's read-only or destructive hints as claims, not facts.
- **The endpoint.** Is it the team's, and is it healthy? A failing server is flagged.
- **Upstream sign-in.** For a server in OAuth mode: the authorization server (its host is highlighted when it differs from the server's), the issuer, how the client was registered, the scopes asked for and those the server supports, and whether the resource indicator is sent.
- **The auth mode and its settings.** For a server in each person's own key mode: where the key goes (a header, a bearer token or a query value, a name and a prefix), because the key goes to this server's address. For a server in the portal's own OAuth client mode: the token endpoint (flagged when it is on another host than the server), the scopes and the hints of the client, and that every caller of the server shares the portal's token.
- **TLS to the server.** When the server has a private CA or a client certificate, the Settings › TLS to the server card shows the CA's and the certificate's fingerprints, subjects and expiry. A CA replaces the system roots for this server, so read it as you would the endpoint: it decides who the portal trusts to be that server. Under **Self-publish** nobody reviews a team's CA change.
- **User authorization.** The provider and scopes the server requires, and any per-capability overrides: these decide which of a person's tokens the server will receive.
- **Send identity token.** Whether people's names, emails and teams go to this server.

Then, on the server's **Company catalog** card:

- **Approve…** › **Approve and publish**: the server is published with its current capabilities approved. It can't be approved until its capabilities have been read from its current URL.
- **Reject…** › **Reject**, with a note for the team (required): it stays private to its team, which sees your note and can fix what's needed and ask again.

### You approve what you read

The review dialog sends the server's **review digest** (a SHA-256 over its URL, auth mode, user authorization requirement, the settings of the key, OAuth client and CA described above, and every listed capability's kind, name and fingerprint) that it showed you when it opened. If the server changed in between (an editor refreshed it after you started reading), the approval is refused with **"changed since review"** (`409 changed_since_review`) and nothing is approved: reload the server, read what changed and approve again. A refresh of a server that is waiting for review is still allowed; it changes the digest.

A published server can be taken off the catalog the same way: rejecting a published server removes it from the catalog and marks it rejected, with your note.

## Approve changed capabilities

When a published server's capability changes, or a new one appears, it stays out of the catalog until approved, while the rest of the server stays published. The server's pending-changes count and the **changes** filter find them. On the Capabilities tab, read the new definition and **Approve change**. The approval names the capability's **fingerprint** you read; if the definition changed again before you approved, it is refused with the same "changed since review" answer. Under **Self-publish**, the team's owners and admins approve their own changes.

## What comes back for review

Under **Approval required**, a published server returns to **Waiting for review** on its own when its URL changes, when it switches to OAuth mode, to each person's own key or to the portal's own OAuth client, to another authorization server or to new scopes, when where a person's key goes, the portal's token endpoint, client, audience or resource changes, when its private CA is added, changed or removed, or when a capability's user authorization requirement widens. It leaves the catalog until you review it again. The team's note and the history say why it's back.

Every decision is in the audit log (`mcp_server.publish`, `mcp_server.reject`, `mcp_capability.approve`); the approval of a server records the digest.

Platform admins get a notification when a server enters review (`publish.requested`), and the team's owners and admins get one when you decide (`publish.decided`): see [Notifications](/docs/administer/notifications). The [overview](/docs/administer/overview) lists servers waiting for review, with the age of the oldest request.

### Scripts that approve

Approving through the management API must say what was reviewed. `adminReviewMcpServer` with `approve` needs `expectedDigest` (the server's `reviewDigest`), and `adminApproveMcpCapability` needs `expectedFingerprint`, or the answer is `400 expected_digest_required` or `400 expected_fingerprint_required`. [Automation tokens](/docs/administer/automation-tokens) can't approve at all: the review gate stays with a person.
