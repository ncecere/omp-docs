Open MCP Portal serves three HTTP surfaces from one origin, its `APP_URL`:

- **The MCP endpoint**, `POST /mcp/{slug}`: one per gateway, Streamable HTTP, for MCP clients and agents. It's JSON-RPC, so it isn't in the OpenAPI document. See [The MCP endpoint](/docs/api/mcp-endpoint).
- **The OAuth endpoints** under `/oauth/` and `/.well-known/`: the authorization server MCP clients sign in with, and the JWKS MCP servers verify identity tokens with. See [OAuth endpoints](/docs/api/oauth-endpoints).
- **The management API** under `/v1`, plus `/auth/*` and the health checks: everything the web app does. It's described by an OpenAPI 3.0 document that covers every route (a test in the product repository enforces it). See the [reference](/docs/api/reference/operations/getHealthz), generated from that document.

## The management API

The management API serves the web app, and, for a limited set of operations, CI and scripts. It **may change between releases** before 1.0.

Conventions:

- **Authentication.** Browser sessions (a cookie) call every operation. [Automation tokens](#automation-tokens) (`ompadm_…` and `omppub_…`) call only the operations marked for them. Personal API keys (`omp_…`), service account keys (`omp_sa_…`) and OAuth tokens are MCP credentials: they are refused here with `401 invalid_token`.
- **Responses** are `{"data": ...}` on success and `{"error": {"code": "...", "message": "...", "details": ...}}` on failure. Every response carries `X-Request-ID`.
- **Writes from a browser session** need the session's CSRF token in `X-CSRF-Token` (from `GET /v1/me`) and a same-origin `Origin`. Token requests need neither. JSON bodies are decoded strictly: unknown fields are refused.
- **Edits** use revisions: objects carry a `revision` and an `ETag`, and updates send `If-Match`. A missing `If-Match` is `428`, a stale one `412`.
- **Approvals name what was reviewed.** Approving a server sends the `expectedDigest` from `McpServer.reviewDigest`; approving a capability sends its `expectedFingerprint`. Without it the answer is `400 expected_digest_required` or `400 expected_fingerprint_required`; if the server or capability changed since, `409 changed_since_review` and nothing is approved. Publishing may send `expectedDigest` too.
- **Lists** use cursors (`cursor`, `limit`, 50 by default, at most 200) and search with `q`.
- **IDs** are UUIDs; teams, servers and gateways also have immutable slugs.
- **Not allowed and not found look alike**: people outside a team get `404` for its objects.
- **Rate limit**: `REQUESTS_PER_MINUTE` per person or per token (600 by default), `429` with `Retry-After`.

The tags group the routes: sign-in, me, teams, MCP servers, catalog, gateways and calls, API keys, OAuth consent and connected apps, service accounts, auth providers, connections, limits, retention, usage, notifications, automation tokens and admin. New in v0.2.0: `GET /v1/admin/overview` ([Admin overview](/docs/administer/overview), [reference](/docs/api/reference/admin/adminGetOverview)), `GET /v1/teams/{team}/attention` ([Team attention](/docs/teams/attention-and-notifications), [reference](/docs/api/reference/teams/getTeamAttention)), the notification operations (inbox, preferences, destinations, deliveries; see [Notifications](/docs/administer/notifications)), the automation token operations, and `POST /v1/connect/requests/{requestId}/confirm` ([Connecting accounts](/docs/use/connecting-accounts#allowing-a-server), [reference](/docs/api/reference/connections/confirmConnectRequest)).

New in v0.3.2: six operations for people's own keys for servers, all **browser session only** and with no automation token scope, so no token, API key, service account or agent can enter, read or remove a key: `GET /v1/me/server-secrets` ([reference](/docs/api/reference/me/listMyServerSecrets)), `PUT` ([reference](/docs/api/reference/me/setMyServerSecret)) and `DELETE /v1/me/server-secrets/{serverId}` ([reference](/docs/api/reference/me/revokeMyServerSecret)), `GET /v1/connect/secret-requests/{requestId}` (what a link is for; [reference](/docs/api/reference/connections/getSecretRequest)), and `GET /v1/admin/users/{userId}/server-secrets` with `DELETE …/{serverId}` for platform admins and auditors ([reference](/docs/api/reference/admin/adminListUserServerSecrets), [remove](/docs/api/reference/admin/adminRevokeUserServerSecret)); see [Keys for servers](/docs/use/keys-for-servers). `McpServer`, `McpServerCreate` and `McpServerUpdate` gain `personSecret` (placement, name, prefix, label and help), `machineOAuth` (token endpoint, client ID and secret, method, scopes, audience and resource; the secret is never returned) and `tls` (a CA bundle, a client certificate and key, or `clear`; answers carry fingerprints, subjects, issuers and expiry, never the key), and `authMode` accepts `person_secret` and `machine_oauth`. An automation token gets `403 token_not_allowed` for `personSecret`, `machineOAuth`, `tls` and a switch into either secret mode ([Publisher tokens](/docs/teams/publisher-tokens)). `McpErrorClass` gains `tls`, the publish request's reason gains `upstream_tls_changed`, `key.expiring` carries `server_certificate` and `server`, and the attention kinds gain `server_certificate_expiring`. New error codes include `invalid_tls`, `tls_key_required`, `client_secret_required`, `invalid_machine_oauth` and, on the key page, `server_changed`. See [Register a server](/docs/teams/register-a-server#authentication-modes).

New in v0.3.1: `GET` and `PUT /v1/admin/auth-providers/{providerId}/access` ([reference](/docs/api/reference/admin/adminGetAuthProviderAccess); who may use an auth provider, `If-Match` on the provider's revision, browser session only, so no automation token), a `team` and `serverId` filter on [`GET /v1/auth-providers`](/docs/api/reference/auth-providers/listAuthProviders) for the requirement picker, `accessMode` and `narrowOnRefresh` on auth providers ([Auth providers](/docs/administer/auth-providers#who-may-use-a-provider)), `narrowsScopes` on connections, `credentials` (up to eight parts, with no values in answers) on [creating and updating a server](/docs/api/reference/mcp-servers/createTeamMcpServer) in place of `authHeaderName` and `authValue` ([Register a server](/docs/teams/register-a-server#static-credential)), and `traceId` and `traceUrl` on call records ([Tracing](/docs/operate/tracing#the-trace-id-on-a-call)). New error codes include `provider_not_allowed`, `credentials_in_use`, `too_many_credentials`, `invalid_credential_kind`, `invalid_auth_query`, `invalid_auth_value` and `invalid_credential`.

New in v0.3.0 ([Agent platforms](/docs/administer/agent-platforms)): the trusted agent platform operations under `/v1/admin/agent-platforms` (list, create, read, update, delete, test the keys, list relays, and mark or clear a service account as a relay; browser session only, platform admins), `PUT /v1/teams/{team}/mcp-servers/{serverId}/capabilities/{capabilityId}/present-person` ([reference](/docs/api/reference/mcp-servers/setTeamMcpCapabilityPresentPerson)), and under `/v1/me/connections/{connectionId}` the operations that list the servers a person can allow, allow one and take one back (`allowable-servers`, `allow-server`, `allowed-servers/{serverId}`; [Connecting accounts](/docs/use/connecting-accounts#allow-servers-from-my-connections)). Service account objects show their relay platform, and call records name the agent, the platform and the person for a relayed call. None of these accepts an automation token. New in v0.2.2: `POST /v1/teams/{team}/mcp-servers/identity-default` ([reference](/docs/api/reference/mcp-servers/getTeamMcpServerIdentityDefault); the add form's helper for the default of [Send identity token](/docs/teams/register-a-server#send-identity-token), session only), an `identitySent` field and filter on call records, an optional `openRegistration` in [`PUT /v1/admin/settings/oauth-clients`](/docs/api/reference/admin/adminUpdateTrustedClients) and its answer, and `OAuthGrant.expiresAt` (when an app has to sign in again).

## Automation tokens

An automation token authenticates a request to `/v1` with `Authorization: Bearer <token>`:

```sh
curl -H "Authorization: Bearer $OMP_TOKEN" https://mcp.example.com/v1/token
```

- A request with an `Authorization` header is treated as a token request and only that: a cookie sent with it is ignored. It must be exactly `Bearer <token>`.
- A token works only on operations whose OpenAPI description carries `x-omp-token-scopes`, and only if it holds one of the scopes listed there (a write scope includes its read scope). Any other operation answers `403 token_not_allowed`. The four operations that create or revoke tokens answer `403 session_required`: a token can never make or end tokens.
- **Platform tokens** (`ompadm_`, scopes `platform:read` and `platform:write`) read the platform's state and provision teams, gateways, grants and limits. **Team publisher tokens** (`omppub_`, scopes `servers:read` and `servers:write`) work on one team's servers; on another team's path they get `404 team_not_found`.
- [`GET /v1/token`](/docs/api/reference/automation-tokens/getToken) returns the calling token's kind, name, scopes, team and expiry, which helps when debugging a pipeline.
- Tokens never work on `/mcp/{slug}`.

See [Automation tokens](/docs/administer/automation-tokens) (platform) and [Publisher tokens](/docs/teams/publisher-tokens) (team) for creating and using them.

## Keeping the reference current

The reference is generated at build time from `openapi/open-mcp-portal.yaml` in this documentation's repository, a copy of `api/openapi.yaml` from the Open MCP Portal release these docs describe (v0.3.2). The product repository's copy is the source of truth.
