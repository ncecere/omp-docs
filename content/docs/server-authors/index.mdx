Your MCP server keeps running where your team runs it. Open MCP Portal connects to it as an MCP client over **Streamable HTTP**, reads its capabilities, and forwards the calls people and agents make through gateways. These pages are about what reaches your server and how to trust it.

## What your server receives

- **Discovery.** When the server is registered, refreshed or its URL changes, the portal opens a session (it tries the 2026-07-28 revision first and falls back to `initialize` for an older server; see [MCP protocol support](/docs/server-authors/mcp-protocol#era-negotiation)) and lists every kind of capability you advertise: tools, prompts, resources and resource templates, page by page (at most 500 per kind). It never calls a tool to discover it.
- **Health checks.** Every few minutes (5 by default), an MCP exchange to see that you answer. Plus a check whenever someone presses **Test connection** or **Refresh capabilities**. A manual Test carries an identity token for the editor who pressed it ([what a Test sends](/docs/server-authors/identity-token#what-a-test-sends)); refresh and the scheduled checks carry none.
- **Calls.** `tools/call`, `prompts/get` and `resources/read`, only for capabilities a gateway selected and a caller was allowed to use. Lists never reach you: clients get the definitions the portal stored and approved.

The portal is stateless: it keeps no session with you between calls. To an older server, each call is its own MCP session with a new `initialize` handshake; to a 2026-07-28 server, each call is one request. Answer in JSON or as an SSE stream; the portal reads either. If you send `notifications/progress` for the call's progress token, the portal can stream it to a client that asked for it.

Every forwarded call carries the [identity token](/docs/server-authors/identity-token) (unless your team turned off **Send identity token**, which is also the default for a new server with no authentication on a public host), your static header if you registered one, and where relevant a [provider token](/docs/server-authors/provider-tokens) or, for an [OAuth-protected server](/docs/server-authors/oauth-servers), the person's own bearer token. The caller's own API key or OAuth token **never** reaches you.

## What the portal does with your answers

- Names: clients see your tool `check_outage` of server `status` as `status__check_outage`, and your resource `status://services` as `omp://status/status://services`. A `resources/read` arrives with your own URI (the prefix is stripped), and `contents[].uri` in your answer is rewritten for the client.
- `_meta["io.modelcontextprotocol/serverInfo"]` is removed from results: clients talk to the portal, and your server's name and version aren't theirs to see. Other `_meta` entries pass through.
- `structuredContent` that isn't a JSON object is dropped from results, and an `outputSchema` that isn't an object is dropped from tool lists, as the MCP schema requires.
- Requests and responses are limited to 1 MiB, and every exchange to your server's timeout (1 to 120 seconds, set by your team).
- Redirects are never followed. The portal never offers you sampling or roots, and never relays yours. It declares elicitation to a 2026-07-28 server only when the calling client did, and then relays your `input_required` questions to that client. See [MCP protocol support](/docs/server-authors/mcp-protocol#elicitation-relay).

## Definitions are reviewed

What you list (names, titles, descriptions, schemas) is shown to models as instructions, so platform admins review it before it reaches the catalog. When a definition changes on a published server, that capability leaves the catalog until the change is approved. Keep descriptions stable and honest, and don't put data that changes between calls in definitions: use `_meta`, which the portal leaves out of fingerprints. See [Capabilities and change detection](/docs/teams/capabilities).

Annotations (read-only, destructive, idempotent and open-world hints) are shown to people but never trusted for any decision.

## Your server decides what callers may do

The portal has already checked that the caller may use this tool through this gateway. Your server still decides what they may do with it: read the identity token's `principal_type`, `sub`, `email` and `teams` and apply your own rules.
