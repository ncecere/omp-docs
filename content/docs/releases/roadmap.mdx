This is the plan after [v0.2.0](/docs/releases/v0-2-0): an order of work, not a schedule. The detailed version, with the decisions behind it, is the repository's [roadmap](https://github.com/ncecere/open-mcp-portal/blob/main/docs/roadmap.md). Plans change; each release's notes are the record of what shipped.

## What it is, and what it is not

Open MCP Portal is a portal for MCP servers: teams register them, a catalog lists them, gateways curate them, and people and agents get governed access. It is not an LLM gateway, an agent runtime, a workflow engine or a retrieval system, and none of those are planned.

Also decided against:

- **Hosting stdio servers.** The portal never runs MCP servers. Servers are remote and speak Streamable HTTP; a team with a stdio server runs a bridge beside it and registers the bridge.
- **Sampling, roots and logging.** The MCP 2026-07-28 revision deprecates them, so new work does not add them.
- **The old HTTP+SSE transport** for upstream servers, deprecated by the same revision.

## v0.2: MCP 2026-07-28 and a team pilot

Released as [v0.2.0](/docs/releases/v0-2-0) on 2026-10-18:

- **MCP 2026-07-28 alongside the earlier revisions**, chosen per request, toward clients and toward your servers (era negotiation, relaying a server's elicitation requests, streaming progress, trace context), with the conformance suite's results. See [MCP protocol support](/docs/server-authors/mcp-protocol).
- **Pilot readiness:** the [admin overview](/docs/administer/overview), [notifications](/docs/administer/notifications) and scoped [automation tokens](/docs/administer/automation-tokens), and fixes from a security review.

A real deployment is done on one cluster (Authentik sign-in, a database with continuous archiving and daily backups, and a tested restore). Still open from this stage: a written compatibility matrix tried with real VS Code and Cursor against the 2026-07-28 revision (Claude Code has been run), and a feedback channel for the pilot.

## v0.3: credentials and tool policy

- **Credentials for every kind of server:** per-person API keys or tokens, more header and query-string shapes, Basic auth, machine OAuth, mTLS, and shared team connections that service accounts can use.
- **Tool policy:** tools classified as read, write or destructive; credentials, grants and clients limited by class or by named tool; argument constraints and renamed or re-described tools per gateway; **approval before sensitive calls**; requests for gateway access.
- **Reliability and observability:** per-server limits, retries, failover across several URLs, OpenTelemetry tracing, dashboards and alert rules, and long-running tools through the tasks extension.

## v0.4: identity lifecycle, compliance and scale

SCIM and SSO-group mapping so leavers lose access automatically; audit streaming to a SIEM, call-log export, legal holds, and per-person data export and deletion; server governance (owner, data sensitivity, re-review dates, deprecation); secrets-manager and KMS support; a Helm chart, autoscaling, HA PostgreSQL guidance and a backup runbook; and `subscriptions/listen` for list-change notifications.

## v0.5: developer experience and catalog

A command-line tool, a GitHub Action and a Terraform provider, a try-a-tool console for server authors, a better catalog (categories, icons, per-server README, verified badge, search across tools), tool search for large catalogs, and chargeback reports.

## Later

Scanning of tool arguments and results for prompt injection and data loss is wanted but not scheduled.

## Still to verify from v0.1.0

Real Google and Microsoft providers for delegated credentials, VS Code and Cursor over OAuth, and the Kubernetes manifests on a real cluster. See the [v0.2.0 notes](/docs/releases/v0-2-0#known-limitations).
