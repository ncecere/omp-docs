This is the plan after [v0.2.1](/docs/releases/v0-2-1): an order of work, not a schedule, for one maintainer. Every item is an open
GitHub issue with its implementation plan (data model, API, the code to change, tests, acceptance criteria and open questions), grouped
into [milestones](https://github.com/ncecere/open-mcp-portal/milestones). The repository's [roadmap](https://github.com/ncecere/open-mcp-portal/blob/main/docs/roadmap.md) has the same plan with each item's summary and dependencies.

## What it is, and what it is not

Open MCP Portal is a portal for MCP servers: teams register them, a catalog lists them, gateways curate them, and people and agents get governed access. It is not an LLM gateway, an agent runtime, a workflow engine or a retrieval system, and none of those are planned.

Also decided against:

- **Hosting stdio servers.** The portal never runs MCP servers. Servers are remote and speak Streamable HTTP; a team with a stdio server runs a bridge beside it and registers the bridge.
- **Sampling, roots and logging.** The MCP 2026-07-28 revision deprecates them, so new work does not add them.
- **The old HTTP+SSE transport** for upstream servers, deprecated by the same revision.

## Where things stand

- **[v0.1.0](/docs/releases/v0-1-0)** (2026-10-17): registry and catalog, gateways, OAuth for MCP clients, service accounts, delegated credentials, per-person OAuth to upstream servers, operations.
- **[v0.2.0](/docs/releases/v0-2-0)** (2026-10-18): MCP 2026-07-28 next to every earlier revision, an admin overview, notifications, automation tokens, and fixes from the threat model.
- **[v0.2.1](/docs/releases/v0-2-1)** (2026-10-18): Test connection exercises the identity token, a cap on open client registration, and a Kubernetes smoke test in CI.

Proven on a real deployment (Authentik sign-in, a database with continuous archiving and daily backups, a restore tested twice): Claude Code over OAuth and an API key on
the 2026-07-28 revision, per-person OAuth to GitHub's hosted MCP server, and DeepWiki through a gateway. Not proven yet: VS Code and Cursor, a real Google or Microsoft
provider, a real Slack webhook and mail provider, and a pilot with a real team. Each is an issue below; the [client compatibility](/docs/use/client-compatibility) page says what has been run.

## How the work is ordered

1. **Decide, verify and pilot first.** Three small product decisions ([#5](https://github.com/ncecere/open-mcp-portal/issues/5), [#6](https://github.com/ncecere/open-mcp-portal/issues/6), [#7](https://github.com/ncecere/open-mcp-portal/issues/7)), the real-client checks, and a pilot with one team ([#20](https://github.com/ncecere/open-mcp-portal/issues/20)). What the pilot finds decides the order inside v0.3.
2. **v0.3 starts with what is independent and low-risk** (allow-lists for provider tokens, tracing, more credential shapes) while the pilot runs, and holds the large tool-policy work until there is feedback.
3. **Governance builds on classification.** Scopes, argument constraints and approvals all use the read, write or destructive class of a tool ([#28](https://github.com/ncecere/open-mcp-portal/issues/28)), so it comes first.
4. **Operations before scale.** CI that proves upgrades, ingress and restores ([#43](https://github.com/ncecere/open-mcp-portal/issues/43)) comes before the Helm chart ([#42](https://github.com/ncecere/open-mcp-portal/issues/42)).

## Help

The most useful contributions are not code: try a client that has not been run (VS Code, Cursor), run the portal with a real team, or answer one of the decision issues with your use case. See [Client compatibility](/docs/use/client-compatibility), the [issue forms](https://github.com/ncecere/open-mcp-portal/issues/new/choose) and [Discussions](https://github.com/ncecere/open-mcp-portal/discussions).
