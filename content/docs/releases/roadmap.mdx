This is where the plan stands after [v0.13.1](/docs/releases/v0-13-1), the current release: an order of work, not a schedule, for one maintainer. **Development is paused after v0.13.1**; work resumes when the maintainer resumes it, and no dates are promised. **Version 1.0.0 is not decided.** Every open item below is a GitHub issue with its implementation plan (data model, API, the code to change, tests, acceptance criteria and open questions), grouped into [milestones](https://github.com/ncecere/open-mcp-portal/milestones). The repository's [roadmap](https://github.com/ncecere/open-mcp-portal/blob/v0.13.1/docs/roadmap.md) has the same plan with each item's summary and dependencies.

## What it is, and what it is not

Open MCP Portal is a portal for MCP servers: teams register them, a catalog lists them, gateways curate them, and people and agents get governed access. It is not an LLM gateway, an agent runtime, a workflow engine or a retrieval system, and none of those are planned. It is not an impersonation service for external agent platforms either: that integration shipped in [v0.3.0](/docs/releases/v0-3-0) and was retired in [v0.4.0](/docs/releases/v0-4-0). Ordinary MCP clients, coding assistants included, use the portal's standard credentials.

Also decided against:

- **Hosting stdio servers.** The portal never runs MCP servers. Servers are remote and speak Streamable HTTP; a team with a stdio server runs a bridge beside it and registers the bridge.
- **Sampling, roots and logging.** The MCP 2026-07-28 revision deprecates them, so new work doesn't add them.
- **The old HTTP+SSE transport** for upstream servers, deprecated by the same revision.

Content scanning (prompt injection and data loss) is wanted but not scheduled. Its design is written (#52, decision 87) and proposes a narrow first slice in shadow mode, with no hosted model. **No scanner is built.**

## How the work is ordered

1. **Verify and pilot alongside the code.** The real-world checks above need evidence, not more fake-server tests.
2. **Audit before erasure.** The audit stream (#38) comes before legal holds and erasure (#39), because holds need a durable audit tail and erasure reuses the deprovisioning path of #36.
3. **Packaging after the gates.** The Helm chart (#42) builds on the release gates of #43 and the database roles of #44, and uses the existing `ENCRYPTION_KEY` handling since #41 is deferred.
4. **Developer experience on the governed path.** The try-a-tool console (#48) and the tool-search mode (#50) must use the normal call path, with classes, scopes and approvals. Chargeback (#51) needs the calling team recorded at call time.
5. **Scanning in shadow mode first.** Corpus (#70), then definition scanning at refresh (#72), then findings in the review UI (#73). No call-path scanning, blocking or external service.

## Help

The most useful contributions are not code: try a client that hasn't been run (VS Code, Cursor), run the portal with a real team, or answer one of the open decision issues with your use case. See [Client compatibility](/docs/use/client-compatibility), the [issue forms](https://github.com/ncecere/open-mcp-portal/issues/new/choose) and [Discussions](https://github.com/ncecere/open-mcp-portal/discussions).
