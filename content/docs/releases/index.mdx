## Supported versions

Before 1.0, only the **latest minor release** is supported: fixes, security or otherwise, are made on `main` and released as a patch of that minor. Older minors get no fixes, so upgrade to the latest. Today that is **v0.13.1**. See [`SECURITY.md`](https://github.com/ncecere/open-mcp-portal/blob/v0.13.1/SECURITY.md) and [`CONTRIBUTING.md`](https://github.com/ncecere/open-mcp-portal/blob/v0.13.1/CONTRIBUTING.md).

## Before 1.0

- **It is development software.** It has been tested with unit and integration tests against a real PostgreSQL, fake MCP servers and a fake OAuth provider, on Kubernetes release gates, and with real clients and a real upstream server (see each release's notes). It hasn't run in production yet; a pilot is your environment's test.
- **Upgrades only go forward.** Migrations can't be undone by changing images; going back past a migration means restoring a backup, and an older image doesn't enforce what a newer one added. Read every release's notes between your version and the target. See [Migrations and upgrades](/docs/operate/migrations-and-upgrades).
- **A minor release may break things.** v0.4.0 did: it retired external agent-platform trust. Each release's notes say how to adapt.
- **The management API may change** in any minor release before 1.0. The MCP endpoint follows the MCP specification, and the headers MCP servers receive (`MCP-Gateway-Identity`, `MCP-Gateway-Provider`, `MCP-Gateway-Provider-Token`) won't change. Since v0.4.0, a client that **sends** `MCP-Gateway-Identity` to `/mcp/{slug}` is refused with `403`.
- **Version 1.0.0 is not decided.** Releases continue as v0.x until the maintainer decides otherwise.

## How releases are published

Each release is a Git tag, `vX.Y.Z`, with an entry in the repository's `CHANGELOG.md`, notes in `docs/releases/` and a GitHub release. The project follows Semantic Versioning. Releasing a tag publishes the container image `ghcr.io/ncecere/open-mcp-portal:vX.Y.Z` for amd64 and arm64, signed with cosign keyless signing by the repository's `image.yml` workflow, with its SBOM and build provenance attached as attestations. The GitHub release attaches:

- `open-mcp-portal-vX.Y.Z.digest.txt`: the image digest to pin;
- SPDX SBOMs for the image and each platform;
- since v0.10.0, the `omp` command line for Linux, macOS and Windows on amd64 and arm64, each with a cosign bundle (`.sigstore.json`);
- `checksums.txt` for the files.

Check the image's signature with cosign v3.0 or newer before you deploy, and deploy by digest:

```sh
cosign verify ghcr.io/ncecere/open-mcp-portal@sha256:<digest> \
  --certificate-identity https://github.com/ncecere/open-mcp-portal/.github/workflows/image.yml@refs/tags/vX.Y.Z \
  --certificate-oidc-issuer https://token.actions.githubusercontent.com
```

Check an `omp` binary the same way, with `cosign verify-blob` and its bundle, then its checksum:

```sh
cosign verify-blob omp-vX.Y.Z-linux-amd64 \
  --bundle omp-vX.Y.Z-linux-amd64.sigstore.json \
  --certificate-identity https://github.com/ncecere/open-mcp-portal/.github/workflows/image.yml@refs/tags/vX.Y.Z \
  --certificate-oidc-issuer https://token.actions.githubusercontent.com
sha256sum --ignore-missing -c checksums.txt
```

See [The omp command line](/docs/api/cli) for installing it.
