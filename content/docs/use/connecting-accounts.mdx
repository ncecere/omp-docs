Some tools act **as you** on another service: create a GitHub issue as you, search your Gmail, read your Google Drive. Others belong to an MCP server that is OAuth-protected itself, such as GitHub's hosted MCP server, where each person signs in to the server's own service. In both cases Open MCP Portal needs your account on that service once. It keeps the token, refreshes it, and sends it only to a server **you have allowed** to use it. Your AI client and its model never see it.

## The first call: a link instead of a result

The first time you call such a tool, the call isn't forwarded. The portal answers with JSON-RPC error **`-32042`** (`URLElicitationRequiredError` in the MCP specification) carrying a link:

```text
github-tools__create_issue needs your GitHub account (repo). Open
https://mcp.example.com/connect/github?request=Zk3… to connect it, then try again.
```

What your client receives depends on its MCP version:

- **Most clients** get the JSON-RPC error above (`-32042`), and clients that support URL elicitation show the link as a prompt; others show the message, which contains the link.
- A client using the **2026-07-28** revision that supports URL elicitation gets the link as a question it can answer (an `input_required` result), and retries the call with the state it was given.
- A **2026-07-28** client that doesn't support URL elicitation gets a tool error with the link in its text (ending "Open the link to connect it, then try again."), because that revision forbids `-32042` for such a client. A prompt or a resource read gets error `-32010` with the link in the message.

In every case it is the same link. Open it in your browser:

1. If you aren't signed in to the portal, you sign in first. The sign-in page says "A tool needs one of your accounts".
2. The confirm page shows who you're signed in as, the tool that asked, the gateway, the service, the **MCP server and its team** that will receive your account, the account connected now, and **each permission (scope)** asked for, marked as already allowed or new. Nothing has been sent to the service yet.
3. Choose **Continue to &lt;service&gt;** (for an MCP server in OAuth mode, **Continue to sign in**) and approve at the service. Or **Cancel**: nothing is connected. If your account already has every permission the server needs, the page asks only **Allow &lt;server&gt; (&lt;team&gt;)**: confirming records your permission and doesn't go to the service.
4. The result page says whether it worked. Go back to your AI client and **run the tool again**.

The link works **only for you** (it isn't a sign-in link: it needs your own browser session with the portal), **only once**, and for **10 minutes**. Opened by someone else, it shows "This link was made for someone else". Expired or used, it shows "This link expired": run the tool again for a new one. Calling the same tool again while a link is still valid returns the same link.

## Allowing a server

Since v0.2.0, a connected account isn't sent to every server that names the service. **Each person allows each server once.** The consent page names the server and the team that runs it ("Allow Shared mailbox (Support Tools) to use your Google account"), so you can tell whether you know and trust it.

<Screenshot slot="connect-allow-server" />

Only then does that server receive your token for the service, at the address it had when you allowed it, for the permissions the page showed.

- **First call to a new server:** the call asks for your permission with a link, the same way as the first connection (the reason behind it is `server_not_allowed`). Nothing was forwarded.
- **Your connection lists the servers you allowed**, with the team and the address. See My connections below.
- **If a server moves to another host or port, or starts requiring another service, your permission for it ends**, and the next call asks again. A change that only touches the path doesn't. Disconnecting a service ends your permissions for all its servers.
- **After the upgrade to v0.2.0** nobody had allowed any server, on purpose, so you are asked once per server. A link made before the upgrade is refused as expired: run the tool again.
- A link is made for **one server**: it can't allow another. If the server moved or changed service after the link was made, the link is refused and nothing is recorded; run the tool again.

Allowing a server gives it your token for the service, which holds **every permission you have ever granted that service**, not only the ones this server asked for. Allow only servers you trust. The portal doesn't narrow the token per call yet.

### Allow servers from My connections

You can also allow a server **without making a call**. On Account › **My connections**, choose **Allow servers…** on a connection. The dialog lists the servers that need that service and that you can use through a gateway now (your teams' servers on gateways you can use, and published servers on gateways you have access to), each with its team, its address and the permissions it asks for. Choose **Allow** for the ones you trust. A server that isn't on a gateway you can use isn't listed and can't be allowed.

<Callout type="info" title="Why this exists: agents">
An AI agent acting for you through an [agent platform](/docs/administer/agent-platforms) can't open a link. When its call needs something you haven't set up, the tool answers with a **link-free message** that says what to do, for example "github__create_issue needs you to allow Status (Support Tools) to use your GitHub account (repo), which you haven't. Allow Status under Account › My connections in Open MCP Portal, then try again." Do that, then ask the agent again.
</Callout>

Allowing records the same permission a consent link's confirm step would: the server's address now and the permissions it requires, with nothing sent to the service. It is your own act in your browser session: an API key, an automation token, a service account or an agent can't do it for you, and it is audited. If the connection doesn't have the permissions yet, the dialog offers **Grant more access**, which is the normal round trip to the service. If the server moved or asks for more than the list showed when you pressed **Allow**, nothing is recorded and you're asked to look again. Each server you allowed is listed on its connection, and **Take back** removes one server's permission without disconnecting the account.

### When the result page says something else

| Result | Means |
|---|---|
| Connected | Run the tool again |
| Some of the permissions weren't allowed | The service granted fewer scopes than the tool needs. Run it again and allow everything asked for; if the service doesn't offer a scope, tell the server's team |
| Denied | You (or the service) declined. Nothing changed |
| This attempt expired | Connecting has to finish within 10 minutes. Run the tool again |
| Sign in as the person who started connecting | Your browser is signed in to the portal as someone else, so nothing was connected |
| Couldn't connect | Something failed at the service and nothing changed. If it keeps failing, ask a platform admin to check the provider's settings |

## Connecting ahead of time

You don't have to wait for a tool to ask:

- **My gateways** › a gateway › **Accounts it needs** lists each service the gateway's tools need, with **Connect** buttons.
- Account › **My connections** › **Connect an account** connects a service with its default permissions.

## My connections

Account › **My connections** lists your connected accounts: the service (or MCP server, with an "MCP server" badge and its team), the account it is (such as your GitHub login), the permissions granted, the **servers you allowed** to use it (name, team and address; read-only), the status, when it was last used and when the token expires. From there you can **Connect**, **Reconnect**, **Disconnect**, and use **Allow servers…** to allow or take back a server (see above).

<Screenshot slot="my-connections" />

- One connection per service. Connecting again asks for everything granted before plus anything new, so a new token never loses permissions.
- The portal refreshes tokens shortly before they expire. If a refresh is refused (for example you revoked the app at the service), the connection shows that it needs you to connect again, and the next call answers with a new link.
- **Disconnect** erases the tokens and your permissions for servers at once and, where the service supports it, revokes the tokens there too.
- Leaving a team doesn't change your connections: they are yours. If you're suspended, they're kept but every request you make is refused.

Platform admins can see the metadata of anyone's connections (never the tokens) and disconnect them; auditors can see them.

## MCP servers you sign in to

For a server in OAuth mode, the link reads, for example, "github__get_me needs you to sign in to GitHub MCP (repo …)", and the confirm page names the server, its sign-in host (such as github.com) and each scope. Two more cases ask you again:

- the server stops accepting your token (it answers `401`): the portal refreshes once and retries; if that fails, the next call answers `-32042` with a new link;
- the server asks for more access (`403 insufficient_scope`) within the scopes its team had reviewed: the next call answers `-32042` asking for them.

Anything else the server refuses comes back as `-32010` with the reason.

## Service accounts and agents

Service accounts can't use tools that act as a person: their calls answer `-32010` with `data.reason` `service_account`. Those tools still appear in lists, marked "Service accounts can't use this" in team views. The exception is an agent that an [agent platform](/docs/administer/agent-platforms) relays *for you*: the call is yours, uses your connections, and never gets a consent link (a tool error tells you where to connect or which server to allow).
