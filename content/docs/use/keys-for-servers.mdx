title: Keys for servers
description: Some MCP servers want your own API key or token. Where to paste it once, who can use it, how to let your agents use it, what to do when a server refuses it, and what nobody can see.
---

Some MCP servers don't sign you in with OAuth; they want **your own API key or token**, such as a personal key from the service's settings page. A team can set a server up so that each person pastes their own key into Open MCP Portal once. The portal then sends your key, and only yours, with your calls to that server. Your AI client and its model never see it.

This page is for the person who enters a key. The team that registers such a server follows [Each person's own key](/docs/teams/register-a-server#each-persons-own-key).

## The first call: a link to paste your key

The first time you call a tool of such a server, the call isn't forwarded. The answer carries a link, in the same three shapes as a [connected account's link](/docs/use/connecting-accounts#the-first-call-a-link-instead-of-a-result): a JSON-RPC `-32042` error for most clients, an `input_required` result for a 2026-07-28 client that supports URL elicitation, and a tool error (or `-32010` for a prompt or a read) with the link in its text otherwise. Open it in your browser:

1. If you aren't signed in to the portal, you sign in first.
2. The page names **the server, its team, the address the key goes to and how it is sent** (a header, a bearer token or a query value), and what the team calls the key, with the team's note on where to find it.
3. Paste the key in the password field and save.
4. Go back to your AI client and **run the tool again**.

The link works **only for you**, **only once** and for **10 minutes**. Expired or used, run the tool again for a new one. If the page names a server or an address you don't know, don't paste anything: the key goes to that address.

## Keys for servers on My connections

Account › **My connections** › **Keys for servers** lists the servers where you can enter a key, and every key you have entered. You can enter a key ahead of time, replace it or remove it there.

- **Nobody can read a key back, you included.** Pages and the API show only its last four characters, and only when it has at least eight. Keys are 8 to 4,096 characters on one line.
- **A key belongs to one server's address.** If the team moves the server to another origin (scheme, host or port), or changes where the key goes (for example from a header to a query value), everyone's keys for it are deleted and you are asked again. A change that only touches the path keeps them.
- **Rejected keys.** If the server answers a call with `401` or `403`, your key is marked **rejected**: it isn't sent again, nothing is retried, and you are asked to enter it again. A `403` that is only a permission problem on one tool does the same, so enter the key again once the permission is fixed.
- **Remove** a key to stop it being used. Platform admins can also remove anyone's key (never read it).
- **Suspension** keeps your keys but blocks every call you make; reactivating restores them. Deleting your account deletes them.

Only the person who entered a key can use it. A key is never shared with your team, and **a service account has no key**: its calls to such a server are refused (`-32010`, reason `service_account`).

## Let my agents use this key

An AI agent acting for you through an [agent platform](/docs/administer/agent-platforms) uses your key only if you switch on **Let my agents use this key** for that server. It is **off by default**. With it off, or with no key entered, the agent's call is refused with a tool error that names where to go (Account › My connections); it **never gets a link**, because an agent can't open one. Switch it off, or remove the key, to stop agents using it. Until then, an agent platform you allowed keeps using your key.

## If you are an editor: use my key to read this server's capabilities

When a team adds a server that wants each person's key, the portal has no key yet to read the server's tools with, so the server is created without its capabilities. An editor, admin or owner of the team enters their own key and chooses **Use my key to read this server's capabilities**. The portal then reads the server with that key, and **Test connection** and **Refresh capabilities** use it too; the server's Overview says whose key it is. You can do this before any gateway offers the server.

That key is used only for those reads, and only while you are an active editor of the team and the key is active and entered for the server's address now. **Scheduled health checks never send anybody's key**: a server that answers `401` or `403` to one still counts as healthy ("Reachable — requires sign-in").

## What the portal does with your key

- It is **sealed** with the installation's `ENCRYPTION_KEY`, per person and server. It isn't returned by any API, and it isn't written to logs, the audit log, call records, recorded call contents, health messages, errors or traces. A server that echoes it back has it removed from the answer, in its plain, prefixed and URL-encoded forms.
- **A query key travels in the URL.** If the team chose a query value, the server and any proxy in between may log the address. The page you paste into says so.
- **A key is as safe as the server that receives it.** It goes in the clear to that server (over TLS).
- Every change you make is in the audit log (`person_secret.create`, `.rotate`, `.revoke` and `.agents_update`, naming you, the server and its origin, never the key).
- No automation token, API key, service account or agent can enter, read or remove a key: these actions work only in your browser session.

## Not covered

Shared team keys, several keys per person and server, per-tool keys and testing a key when you paste it aren't built.

If a call fails, see [Troubleshooting](/docs/use/troubleshooting).
