title: Capabilities and change detection

A server's **capabilities** are what it lists: tools, prompts, resources and resource templates. Open MCP Portal reads them when the server is created, when its URL changes and when an editor chooses **Refresh capabilities** on the **Overview** tab. Gateways and the catalog never contact the server to list them: clients get the definitions the portal stored and approved.

## Reading capabilities

A refresh connects to the server and lists every kind it advertises, page by page. It never calls a tool. Limits keep a misbehaving server from flooding the portal:

- at most 500 entries per kind, and at most 500 pages; a repeated cursor stops the listing;
- each response at most 1 MiB, and a single definition at most 64 KiB (more fails the refresh);
- titles clipped to 200 characters and descriptions to 10,000; names and URIs up to 1,000 characters (longer or invalid entries are skipped).

A kind the server advertises but answers with "method not found" counts as empty. For a server in OAuth mode, the refresh uses the connection of the person who authorized it ("Capabilities read as …"); if that connection lapsed, or that person is no longer an editor or above, the refresh asks someone to authorize again.

The **Capabilities** tab lists what was read, by kind, with each item's description and the hints the server declares (read-only, destructive, idempotent, open world). The portal shows those hints but never trusts them for any decision. What it does trust is the **class** your team gives each tool ([below](#classifying-tools)).

<Callout type="warn" title="Untrusted text">
Names, descriptions and schemas come from the server, and a model reads them as instructions. Read them before you publish a server or approve a change.
</Callout>

## Fingerprints and changes

The portal stores each capability's definition as canonical JSON (sorted keys, without `_meta`, which servers use for data that changes between calls) and its SHA-256 **fingerprint**. On each refresh it compares:

- **Approved** means the current definition is the one that was approved, and the server still lists it.
- **Changed**: on a published server, a definition that differs from the approved one. A changed capability drops out of the catalog and stops being served by gateways that use it as a catalog capability, at once, without anyone acting, until the change is approved.
- **New**: on a published server, a capability listed for the first time isn't approved either.
- **Gone**: a capability the server no longer lists. Its approval is withdrawn; if it comes back, it needs approval like a new one.

A refresh never approves anything. The server's pending-changes count covers changed and new capabilities. Each refresh reports how many were listed, added, changed and gone, and is recorded in the audit log.

Who approves: a platform admin under **Approval required**; the team's owners and admins under **Self-publish** (**Approve change** on the capability, after reading its definition). The approval names the fingerprint that was read: if the definition changed again before the button was pressed, it is refused (`changed_since_review`) and you read it again. Private servers need no approval for the team's own gateways: a team gateway serves the team's own servers' capabilities as they are now. See [Publishing and review](/docs/teams/publishing).

## Classifying tools

A tool's annotations are the server's own claims. A **class** is your team's: **Read** (only observes), **Write** (changes data) or **Destructive** (deletes data or causes irreversible effects). A tool nobody classified is **Unclassified**, which makes no assertion and is never treated as read. Classes decide:

- which tools a [tool scope](/docs/use/tool-scopes) such as **Read only** lets a key, app or service account call;
- which tools an [approval rule](/docs/teams/approval-rules) for a class matches (unclassified tools match destructive rules);
- which tools the portal may [retry or send to a failover endpoint](/docs/teams/protection-and-failover) after a brief failure (read tools only).

<Screenshot slot="capability-classes" />

The team's **owners and admins** classify tools on the **Capabilities** tab: **Classify tools…** on the Capabilities card for many tools at once (at most 500 changed tools per save), or **Classify…** on one tool. The dialog (**Classify tools** or **Classify &lt;tool&gt;**) has a class select per tool, with **Unclassified**, **Read**, **Write** and **Destructive**, and **Use suggestions**, which fills in each tool's suggestion. **Save classes** saves them. Editors, members and platform staff see the classes but can't change them, and automation tokens can't classify.

Each tool shows its class as a badge, **Class: read**, **Class: write**, **Class: destructive** or **Unclassified**, and next to it:

- **Suggested: &lt;class&gt;**: what the server's hints suggest. `readOnlyHint: true` suggests read; otherwise an explicit `destructiveHint: false` suggests write; anything else suggests destructive. A suggestion is never saved by itself: it is untrusted, so read what the tool does before you accept it.
- **Class differs from suggestion**: the saved class and the current suggestion disagree. It's a prompt to look again, not proof that either is wrong.

**Refresh keeps classes**, even when a tool's definition changes. A tool the server stops listing loses its class, and must be classified again if it comes back. If the server changed while the dialog was open, it says "The server changed. Close this dialog and review the refreshed tools before trying again."

**Review.** **Lowering** a class (destructive to write or read, write to read, or giving an unclassified tool read or write) sends a published server back to review under **Approval required** (reason `classification_changed`), and the dialog warns "The server will leave the catalog". Raising a class, clearing it or choosing destructive never does.

**Where classes show up.** Gateways list classified tools with `readOnlyHint` and `destructiveHint` set from the class (read: true and false; write: false and false; destructive: false and true); other annotations, and unclassified tools, keep the server's hints. The [identity token](/docs/server-authors/identity-token) of a call to a classified tool carries `tool_class`, and each call's page shows the **Tool class at call time**, so a later change doesn't rewrite history. Changes are audited as "Changed a tool's class".

## Health

Each server's health comes from checks:

- **Scheduled**: every `HEALTH_CHECK_INTERVAL` (5 minutes by default), the portal checks every enabled server of every active team, four at a time, on one replica.
- **Test connection** on the Overview tab runs a check now. When the server's **Send identity token** is on, it sends the identity token of the editor who pressed it, and fails with a specific message if the server refuses it with `401` or `403` but accepts the request without it. Scheduled checks and refresh send no token. See [Send identity token](/docs/teams/register-a-server#send-identity-token) for what a Test can't catch, and for the switch's default (off for a new server with no authentication on a public host).
- Every **Refresh capabilities** also stores a check.

The **Health** tab's **Upstream health** card lists recent checks, the latest 100 per endpoint: ok or failed, latency, what triggered it, which **Endpoint** was checked (**Primary**, or **Additional endpoint N** for a [failover endpoint](/docs/teams/protection-and-failover#additional-endpoints)), the HTTP status and a short message with secrets redacted. The server's status comes from the primary's checks. A failing server shows since when, on the team's [attention card](/docs/teams/attention-and-notifications), and, after three failed checks in a row, in a notification to the team's owners, admins and editors.

### The protocol it speaks

The server's Overview tab shows the MCP protocol revision the portal last negotiated with it, for example "Protocol 2026-07-28 (modern), negotiated 5 minutes ago". A refresh, a test or a health check updates it, and a new URL clears it. See [MCP protocol support](/docs/server-authors/mcp-protocol#era-negotiation).

| Error | Means |
|---|---|
| Couldn't reach the server | A network error, or an HTTP error other than those below (such as `5xx`) |
| Credentials refused | The server answered `401` or `403` |
| Not found: check the URL | `404` |
| Rate limited | `429` |
| Request refused | `400`, or a JSON-RPC invalid request or invalid params error |
| Unexpected response: is this an MCP server? | The answer wasn't valid MCP, or was cut off |
| Settings problem | The stored header value can't be decrypted (for example after an encryption key change without the previous key) |
| No answer in time | The server's timeout passed |
| Response too large | Over 1 MiB |
| Address not allowed: private, loopback or a redirect | Blocked by the address guard, or the server redirected |
| TLS problem (class `tls`) | The server's certificate isn't trusted, isn't valid for the host name or has expired, the server refused the portal's client certificate or wants one, or it doesn't speak TLS 1.2 or newer. See [TLS to the server](/docs/teams/register-a-server#tls-to-the-server) |
| The portal couldn't get a token for this server | The server uses the portal's own OAuth client and its authorization server is unavailable or refused the client |
| Server concurrency limit reached | The server's [concurrency cap](/docs/teams/protection-and-failover#upstream-protection) was full |
| Server circuit open while it recovers | The server failed 5 times in a row, so the portal paused sending to it for 30 seconds ([circuit breaker](/docs/teams/protection-and-failover#circuit-breaker)) |

For a server in OAuth mode, scheduled checks use nobody's token: an unauthenticated `initialize` that gets the expected `401` challenge for this server counts as healthy, shown as **Reachable — requires sign-in**. **Test connection** uses the setup person's connection.

For a server that wants each person's own key, scheduled checks send nobody's key: a `401` or `403` counts as healthy, shown as **Reachable — requires sign-in**, and **Test connection** and **Refresh capabilities** use the key of the editor who chose to read the server's capabilities. A client certificate that expires within 14 days shows as a warning with the server's health.

## Disabling a server

Turning a server off in **Settings** stops checks and calls, and removes it from the catalog; gateways show its capabilities as unavailable ("Server disabled") until it's turned on again.

To retire a server that people should move away from, deprecate it on the **Governance** card instead: it keeps working, with a banner and notices that name its replacement, until its sunset date, after which no gateway serves it ("Server retired"). See [Server governance](/docs/teams/server-governance#deprecating-and-retiring-a-server).
