---

A gateway is an ordinary MCP server to your code: Streamable HTTP at `<portal URL>/mcp/<gateway slug>`, authenticated with `Authorization: Bearer <key>`. Use the official MCP SDKs; nothing specific to Open MCP Portal is needed.

## Which key

- **A service account key** (`omp_sa_…`) for anything that runs unattended: CI, scheduled jobs, agents in production. The key belongs to a team, not to you, so it keeps working when people change teams. See [Service accounts](/docs/teams/service-accounts).
- **A personal API key** (`omp_…`) for your own scripts and experiments. It acts as you, with your access. See [API keys](/docs/use/api-keys).

Keep keys in your secret store or environment, never in code. Both kinds can be limited to some gateways and to a [tool scope](/docs/use/tool-scopes), such as read-only tools, and both always expire (at most 365 days). A service account can also have an account tool ceiling, which applies on top of each of its keys' scopes.

Name your keys after where they run ("release workflow", "support triage agent"). When a request doesn't carry the MCP client's own name, the key's name is what call records and MCP servers see as the client.

## Python

With the [MCP Python SDK](https://github.com/modelcontextprotocol/python-sdk) (`pip install mcp`):

```python
import asyncio
import os

from mcp import ClientSession
from mcp.client.streamable_http import streamablehttp_client

URL = "https://mcp.example.com/mcp/support"


async def main() -> None:
    headers = {"Authorization": f"Bearer {os.environ['PORTAL_KEY']}"}
    async with streamablehttp_client(URL, headers=headers) as (read, write, _):
        async with ClientSession(read, write) as session:
            await session.initialize()

            tools = await session.list_tools()
            for tool in tools.tools:
                print(tool.name, "-", tool.description)

            result = await session.call_tool("status__check_outage", {"service": "email"})
            print(result.content)


asyncio.run(main())
```

## TypeScript

With the [MCP TypeScript SDK](https://github.com/modelcontextprotocol/typescript-sdk) (`npm install @modelcontextprotocol/sdk`):

```ts
import { Client } from "@modelcontextprotocol/sdk/client/index.js";
import { StreamableHTTPClientTransport } from "@modelcontextprotocol/sdk/client/streamableHttp.js";

const url = new URL("https://mcp.example.com/mcp/support");
const transport = new StreamableHTTPClientTransport(url, {
  requestInit: { headers: { Authorization: `Bearer ${process.env.PORTAL_KEY}` } },
});

const client = new Client({ name: "support-triage-agent", version: "1.0.0" });
await client.connect(transport);

const { tools } = await client.listTools();
console.log(tools.map((t) => t.name));

const result = await client.callTool({ name: "status__check_outage", arguments: { service: "email" } });
console.log(result.content);

await client.close();
```

## Names

Tools and prompts are named `{server-slug}__{name}`, so tools of different servers never clash: the `check_outage` tool of the server `status` is `status__check_outage`. A gateway's owners can give a tool another name on that gateway. Resources are `omp://{server-slug}/{uri}`; read them with the URI exactly as listed. List first rather than hard-coding names: the list shows only what this key may use right now.

For a tool its team has classified, `tools/list` sets `readOnlyHint` and `destructiveHint` from that class, whatever the server declared.

## How the endpoint behaves

- **Stateless.** The portal keeps no MCP session between requests, and any replica can answer. It answers `POST` only (`GET` and `DELETE` are `405`); the SDKs handle that.
- **Lists come from the portal.** `tools/list`, `prompts/list`, `resources/list` and `resources/templates/list` are served from the definitions the portal approved, without contacting the MCP servers. Calls are forwarded.
- **Limits.** Requests and responses are at most 1 MiB. A call waits at most the server's timeout (up to 120 seconds).
- **Retries and failover you don't see.** Read-class tools, prompts and resources may be retried up to twice within that same timeout, and a call may move to one of the server's additional endpoints. Your client still gets one answer per request.
- **No sampling or roots** are forwarded to your client. A server's elicitation questions reach only a 2026-07-28 client that declared elicitation, and never for a call that needed approval. See [MCP protocol support](/docs/server-authors/mcp-protocol#elicitation-relay).
- **Streaming.** A `tools/call` with a progress token from a client that accepts `text/event-stream` is answered as a stream of progress events and then the result. Other calls are one JSON response.

## Errors to handle

| What you get | Means | Do |
|---|---|---|
| HTTP `401` | The key is wrong, revoked or expired; or the person is suspended; or the service account is turned off or its team archived | Fix the key |
| HTTP `403` "Inbound external identity is retired" | The request carries an `MCP-Gateway-Identity` header, which the portal no longer accepts from callers | Remove the header and use an ordinary key |
| HTTP `404` | The gateway doesn't exist, is turned off, or this key can't use it (including a key limited to other gateways) | Check the URL and the key's gateways |
| HTTP `429`, JSON-RPC `-32029` | A rate limit, including the server's own quota or concurrency cap (`data.limit` is `server_per_minute` or `server_busy`); `Retry-After` says how many seconds to wait | Wait and retry |
| JSON-RPC `-32602` "Unknown tool" | The tool isn't on this gateway for this key now: not selected, a higher team role needed, outside the key's [tool scope](/docs/use/tool-scopes), its server unavailable, retired or labelled above the gateway's sensitivity ceiling, or the gateway's policy for it needs review | List again |
| JSON-RPC `-32602` "argument X is fixed by this gateway" or "argument X is not allowed by this gateway" | The gateway fixes that argument's value or allows only some values | Use the values in the listed schema |
| JSON-RPC `-32602` "The tool or its gateway policy changed; retry the original request" | The tool's definition or gateway policy changed during the call | List again, then retry |
| JSON-RPC `-32042` | The tool needs the person's account on another service, or their permission for this server to use it; or the call needs a person's [approval](#calls-that-need-approval). The error's message and `data.elicitations[0].url` carry a link a person opens in their browser. A 2026-07-28 client gets the same link as an `input_required` result, or as a tool error | Show the link to the person, then retry |
| JSON-RPC `-32010` | Refused for a stated reason in `data.reason`: for example `service_account` (a server that wants each person's own key), `service_connection_missing` and the other `service_connection_*` reasons (below), `provider_disabled`, `provider_unavailable`, `circuit_open` (the server failed repeatedly; `data.retryAfterSeconds` says when to try again), `approval_unavailable` or `authority_changed` | Don't retry blindly |

A tool's own failure comes back as a normal result with `isError: true`, as MCP specifies. Every code is described in [The MCP endpoint](/docs/api/mcp-endpoint).

## Tools that act as a person

Some tools need an account on another service: a GitHub or Google account, an MCP server in OAuth mode, or a server that wants each person's own key.

- **With a personal key**, the first call answers `-32042` with a consent link; once you have connected the account under Account › [My connections](/docs/use/connecting-accounts), the calls go through. You can connect ahead of time from **My gateways**.
- **With a service account key**, the call never uses a person's account. For a GitHub- or Google-style service, or a server in OAuth mode, it uses a **shared connection** that the team's owners or admins connected, assigned to that service account and allowed for that server ([Service connections](/docs/teams/service-connections)). Without one the call answers `-32010` with `data.reason` `service_connection_missing`, `service_connection_not_allowed`, `service_connection_needs_reconsent` or `service_connection_lapsed`, and the message "… requires an allowed, active shared … connection. Ask your team's owner or admin to review Service accounts > Connections." A server that wants each person's own key can't be used by a service account at all: `-32010` with `data.reason` `service_account`.

## Calls that need approval

A team can require a person's approval for some calls, for example to destructive tools. Such a call isn't forwarded. It answers with a link to `<portal URL>/approvals/<id>` and the message "`<tool>` needs human approval. Open … to review this exact call, then retry.":

- most clients get JSON-RPC `-32042` with the link in `data.elicitations[0].url`;
- a 2026-07-28 client that supports URL elicitation gets an `input_required` result;
- any other 2026-07-28 client gets a tool error (`isError: true`) with the link in its text.

A person who may review it opens the link and approves or denies that exact call ([Approving sensitive tool calls](/docs/use/approvals)). Your code then sends **the identical call again** (same tool, same arguments) while the approval is valid, 15 minutes by default. An approval covers one attempt: a second call asks for a new one. Identical calls while a request is pending get the same link.

- **Denied:** a tool error "Approval was denied. Open …; only an explicit renewal can request another review." Retrying doesn't ask again; a person must choose **Request new attempt** on the request's page.
- **Spent, result unknown:** "Approval was spent, but the upstream result is not confirmed. Repeating this call may duplicate effects." Check the destination before asking for another attempt.
- **`-32010` `approval_unavailable`:** the approval check couldn't run, or the caller already has 20 requests pending. Retry later.

Service accounts can trigger approval requests too. The owners and admins of the service account's team follow them under **Approvals** › **Requested** and are told when one is decided; they can't approve their own service account's calls unless the rule allows it.

## Long-running tools (tasks)

A 2026-07-28 client can ask for a task handle instead of waiting for a long tool call. `server/discover` lists the `io.modelcontextprotocol/tasks` extension when the portal can relay tasks. Declare the extension in each request's client capabilities (`"io.modelcontextprotocol/tasks": {}` under `extensions` in the request's `_meta` `io.modelcontextprotocol/clientCapabilities`); when the server supports tasks, the call returns a task, which you follow with `tasks/get`, `tasks/update` and `tasks/cancel` (each request declaring the extension again, or it fails with `-32021`).

- Calls that need approval and streamed calls (with a progress token) never become tasks.
- A task lasts at most `TASKS_MAX_TTL` (24 hours by default), and each person or service account can have at most `TASKS_MAX_OPEN_PER_PRINCIPAL` (100 by default) unfinished; past that a call answers `-32010` `task_capacity`.
- A handle works only with the credential that started it. An unknown, expired or foreign handle gets `-32602` "Task not found"; a busy task answers `-32010` `task_busy`.

See [Long-running tools](/docs/server-authors/tasks) for what the server has to do.
